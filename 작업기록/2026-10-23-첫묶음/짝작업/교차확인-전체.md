### 지적

#### 중요 1. 설정 파일 미리보기가 확인 전에 파일 속 저장 위치(UNC 포함)를 실제로 건드린다

- 위치: `desktop/앱/서버.cjs:20366-20378`(`settingsPreview`가 저장 위치마다 `settingsFormat.checkFolder` 호출), `desktop/앱/설정파일.cjs:73-86`(`path.isAbsolute` → `fs.statSync` → 쓸 수 있으면 `.voicenote-쓰기확인-*.tmp`를 만들었다 지움).
- 실패 조건: 다른 사람이 보낸 설정 파일의 `storage.audio`가 UNC 경로(`\\어떤호스트\share`)다. 사용자가 '설정 불러오기'에서 파일을 고르기만 해도(확인 버튼을 누르기 전) 서버가 그 경로에 `statSync`를 해서 Windows가 원격 SMB(또는 WebClient의 WebDAV) 접속과 NTLM 인증을 시도한다. 쓰기가 되는 공유면 시험 파일도 만든다. 호출이 동기라 원격이 응답하지 않으면 SMB 시간 제한 동안 로컬 서버 전체가 멈춘다. 확인 뒤에는 회의 사본이 그 원격 폴더로 나간다(이 부분은 미리보기에 경로가 보이므로 판단 보류 3으로 따로 둔다).
- 근거가 된 결정: 원장 Task 4 Ruling "미리보기도 checkFolder로 확인용 파일을 만들었다 지운다 — 미리보기와 적용이 같은 판단을 써야 하므로". 같은 판단을 쓰는 것은 맞지만, 믿을 수 없는 파일의 값으로 확인 전에 쓰기·네트워크 접근을 하는 것은 따로 막아야 한다.
- 재현: 스크래치 `unc확인.cjs`(위 직접 반례 1). 실제 네트워크 전송은 막고 호출 경로만 확인했다.
- 고치는 방향(참고): 불러오기 미리보기·적용에서 `\\`·`//`로 시작하는 경로와 `\\?\`·`\\.\` 장치 경로를 "이 PC의 드라이브 폴더만 적용합니다"로 건너뛴다. 폴더 고르기 창으로 직접 고른 UNC는 그대로 허용해도 된다.

#### 중요 2. push 비밀 검사 훅이 git이 바이너리로 보는 파일(UTF-16 텍스트 등) 안의 키를 보지 못한다

- 위치: `.githooks/push-비밀검사.cjs:49-53`(`git diff --no-color --no-ext-diff`의 `+` 줄만 검사).
- 실패 조건: 키가 UTF-16LE로 저장된 텍스트 파일(Windows PowerShell 5.1의 `>`·`Out-File` 기본 인코딩) 안에 있다. git이 바이너리로 보고 "Binary files differ"만 내므로 실제 키 비교와 `sk-` 모양 검사 둘 다 통과한다. `.gitignore`가 `작업기록/` 전체를 올리도록 허용하고 있어 로그·출력 파일이 들어갈 길이 있다. 사용자 지시가 "API 키 절대 안 올라가게"라 안전망의 구멍으로 본다.
- 재현: 스크래치 임시 저장소에서 같은 합성 값(`sk-abcdef…0123456789`, 실제 키 아님)을 UTF-8 파일과 UTF-16LE 파일로 각각 커밋하고 `check([sha], [])`를 부르면 UTF-8은 "API 키 모양 문자열" 1건, UTF-16은 0건.
- 고치는 방향(참고): `git diff --text`로 바꾸고, UTF-16 BOM이 있는 새 blob은 `git cat-file -p`로 읽어 디코드한 뒤 같은 검사를 한다. 바이너리로 남는 새 파일은 이름 목록을 보여 주고 멈추는 편이 안전하다.

#### 사소 1. 훅이 새 브랜치 범위를 모든 원격 기준(`--not --remotes`)으로 잡는다

- 위치: `.githooks/push-비밀검사.cjs:33`, 내용 diff는 이름 바꾸기 감지가 켜진 기본값(:49).
- 실패 조건: 개인 백업 같은 다른 원격에 이미 올린 커밋을 공개 `origin`에 새 브랜치로 처음 올리면 그 커밋들은 검사하지 않는다. 이름만 바꾼 파일은 내용 줄이 `+`로 나오지 않는다. 지금 원격은 `origin` 하나라 잠재 결함이다. 훅이 받는 첫 인수(원격 이름)로 `--not --remotes=<원격>`을 쓰고 내용 diff에도 `--no-renames`를 주면 된다.

#### 사소 2. Windows 녹음 파일 하나가 손상되면 그 녹음의 정상 결과도 목록에서 빠진다

- 위치: `desktop/앱/회의보관.cjs:137-140`(결과를 읽을 때 원음 목록을 `녹음-*.json`에서 try 안에서 읽음).
- 실패 조건: 옛 `프로젝트-01`에 `녹음-<id>.json`만 깨지고 `회의-<결과id>.json`은 멀쩡하다. 목록에 그 회의가 없고 "읽지 못한 기록 2개"만 보이며 열 수도 없다. 1.2.0과 같은 동작이지만(그때는 목록 전체가 실패) 원음 없이 결과만이라도 보여 줄 수 있다.
- 재현: 스크래치 `녹음손상확인.cjs` → `{"meetings":[],"skipped":2}`.

#### 사소 3. Windows 다시 정리에서 요약은 받았는데 결과 저장이 실패하면 안내 문구가 화면과 어긋난다

- 위치: `desktop/앱/화면/app.js:1166-1179`(`state.minutes`를 새 요약으로 바꾼 뒤 `archiveResult()`), `:1815-1818`.
- 실패 조건: 의견 반영 요약 요청은 성공하고 `POST /api/meetings/:loc`가 503이다. 화면에는 저장 안 된 새 요약과 '회의록 저장' 버튼이 보이는데, 평가 구역 문구는 "다시 정리하지 못했습니다. 평가는 저장되어 있고 앞선 결과는 그대로입니다."이다. 앞선 결과는 디스크에 그대로라 자료 손실은 없고, 체험 1회는 이미 확정된 상태다.

#### 사소 4. Android 의견 반영이 아주 빨리 끝나면 화면이 새 결과를 열지 않는다(코드 추론)

- 위치: `mobile/안드로이드/assets/app.js:353-361`(`state.lastState`가 참일 때만 끝난 회의를 다시 엶), `MainActivity.java:110-111`(서비스 시작 직후 응답), `MeetingService.java:27-30`.
- 실패 조건: 첫 `poll(true)`가 서비스의 `onStartCommand`보다 먼저 상태를 읽고, 다시 정리가 1.5초 폴링 간격 안에 끝난다(같은 의견을 같은 내용의 결과에 다시 줘서 `중간요약` 캐시가 맞거나, 네트워크가 없어 바로 실패). 그러면 `lastState`가 빈 값이라 새 결과를 열지 않고, 실패라도 평가 구역의 "다시 정리하지 못했습니다" 문구가 뜨지 않는다(결과 창 상태 줄만 바뀜). `state.refining`도 남는다. 보통 경로(수 초 걸리는 실제 요청)는 폴링이 '분석 중'을 잡아 정상이다. 기기에서는 재현하지 않았다.

#### 사소 5. 평가 의견의 앞뒤 공백 처리가 두 앱에서 다르다

- 위치: Windows `desktop/앱/회의보관.cjs:316`(`comment.trim()`으로 저장), Android `Store.java:202-206`과 `assets/app.js:280`(입력 그대로 저장).
- 실패 조건: 의견 끝에 줄바꿈을 두고 평가를 저장하면 Windows `평가-*.json`의 `comment`는 줄바꿈 없음, Android는 줄바꿈 포함. 요청에 넣는 `feedback`은 두 앱 모두 trim해서 같다.

#### 사소 6. Windows 사본 기록을 쓰지 못하면 다음 '다시 저장'에서 (2) 사본이 또 생긴다

- 위치: `desktop/앱/사본저장.cjs:112-122`(세 종류를 다 쓴 뒤 한 번에 `writeLog`, 실패하면 예외가 밖으로 나가 원음 사본은 시도도 안 함).
- 실패 조건: 고른 폴더에는 썼는데 앱 자료 폴더의 `사본기록-<결과id>.json`을 쓰지 못한다. 응답은 'all' 실패 한 줄이고, 다시 저장하면 기록이 없어 같은 사본을 `(2)`로 또 쓴다. Android(`Copies.java:129`)는 항목마다 기록을 쓰고 기록 실패를 그 종류의 실패로 알려 두 앱이 다르다.

### 판단 보류(설계가 말하지 않아 판정하지 않은 동작)

1. **1.2.0으로 되돌려 설치할 때**: 1.3.0은 옛 보관함을 다시 분석·다시 정리하면 `slot` 없이 `location: "p1"`인 `회의-*.json`을 그 `프로젝트-0N` 폴더에 쓴다. 1.2.0의 `listMeetings`는 한 파일만 실패해도 목록 전체를 실패시키므로(기준 커밋 `프로젝트보관.cjs`의 `record.slot !== slot`), 1.2.0으로 되돌리면 그 프로젝트의 지난 회의가 통째로 안 열린다. 되돌리기를 지원 범위로 볼지 설계가 정하지 않았다.
2. **같은 의견으로 다시 정리**: 두 앱 모두 같은 입력·같은 의견이면 캐시를 다시 써서(Windows `app.js:1129` `state.summarySteps`는 같은 창 안에서만, Android `Ai.java:157` `중간요약/<해시>.json`) 요금 없이 똑같은 요약을 새 결과 버전으로 하나 더 저장한다. 사용자가 "한 번 더 정리"를 기대했다면 다르다.
3. **설정 파일로 네트워크 폴더 적용**: 중요 1의 미리보기 문제와 별개로, 확인 뒤 UNC 저장 위치를 적용하면 회의 전사·요약·원음 사본이 원격 공유로 나간다. 설계는 "그 PC에 폴더가 있고 쓸 수 있으면 적용"만 말한다.
4. **Windows 사본 쓰기의 동기 실행**: 결과 저장 요청 안에서 원음 전체를 동기로 읽고 써서(`서버.cjs:20302-20309, 20545`, `사본저장.cjs`의 `readFileSync`·`writeFileSync`) 느린 USB·네트워크 폴더에 긴 회의를 쓰는 동안 로컬 서버가 다른 요청에 답하지 않는다. 화면은 '분석 중'으로 기다린다.
5. **Windows 결과 창 내려받기와 사본 .md 모양 차이**: 결과 창의 Markdown 내려받기(`app.js`의 `lines()`)는 회의록형 할 일 줄에서 빈 담당·기한을 빼고, 고른 폴더 사본(`회의문서.cjs`의 `markdown()`)은 "담당 미정 · 기한 미정"을 쓴다. 기준 커밋부터 있던 차이다.

### 집중 검토 다섯 줄 직접 확인

1. 깨진 JSON·`.tmp`·다른 파일: Windows는 `회의보관.cjs:12, 82-85`가 `회의-/녹음-<uuid>.json`만 고르고 읽기 실패를 `skipped`로 센다. Android는 `Store.java:134-149`가 폴더마다 읽기 실패를 센다. 단, 사소 2처럼 녹음 파일 손상은 결과까지 숨긴다.
2. 제목의 금지 문자·이모지·줄바꿈·300자: Windows `artifactPrefix`(`회의보관.cjs:55-58`)는 금지 문자·제어 문자를 `_`로 바꾸고 코드 포인트 80자로 자른다. Android `Copies.safeTitle`은 같고 120바이트 상한이 더 있다(Task 12 S5에 기록됨).
3. 읽기 전용·권한 없음·쓰는 중 실패: Windows는 대상 폴더 안 임시 파일 → 하드 링크(대상 있으면 EEXIST) 또는 `wx` 생성이고, 임시 파일은 언제나 지운다(`사본저장.cjs:50-84`). Android는 `CREATE_NEW`·SAF 생성 뒤 실패하면 문서를 지운다(`Copies.java:62-98`). 회의 저장은 사본 실패와 분리돼 200이다.
4. 같은 날 같은 제목: 이름에 결과 id(Windows 8자, Android 전체)가 들어가 서로 다른 회의끼리는 겹치지 않고, 같은 이름 파일이 있으면 `(2)`를 붙인다(`사본저장.cjs:41-47`, `Copies.java:60,93`).
5. 의견 1,000자 경계: Windows 서버 `summaryInput`(`feedback.length > 1e3`), 결과 저장(`회의보관.cjs:277`), 평가(`:314`), Android `Ai.checkedFeedback`·`Store.finish`·`saveReview`가 모두 UTF-16 단위 1,000자로 같고, 두 화면 모두 `maxlength="1000"`이다.

### 보안 확인(지적 외)

- 소스·시험·문서·작업기록 추가분에 실제 키·서명 비밀은 없다. 추가된 `sk-` 문자열은 합성 값 2개(`sk-only-synthetic-settings-check-0000`, `sk-test-0000…`)뿐이다. 체험 해제 코드 해시는 두 앱 모두 빈 문자열이다(`체험권한.cjs:9`, `TrialAccess.java:19`). 추가된 바이너리 파일은 없다.
- 로컬 서버는 Host·소켓 주소·토큰 머리글을 모든 `/api/`에서, Origin을 GET이 아닌 요청에서 검사한다(`서버.cjs` 요청 처리 시작부). 정적 응답은 `Cache-Control: no-store`다.
- WebView2 마이크 자동 허용은 `IsLocal(e.Uri)`(앱 서버의 scheme·host·port 일치)이고 마이크 종류일 때만이다(`프로그램.cs:141-146, 258-262`).
- 폴더 선택 메시지는 종류(`audio|transcript|summary`)만 받고 경로는 대화상자에서만 나온다(`프로그램.cs:147-167, 216-234`). 화면 코드에 `innerHTML` 같은 HTML 삽입이 없어 화면을 통해 임의 경로를 저장하게 만들 길은 보이지 않았다. 남는 경로는 설정 파일 불러오기(중요 1, 판단 보류 3)다.

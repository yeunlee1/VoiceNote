- 작성: 2026-10-23, Claude(주작성자). Android 조사는 Codex 짝, 데스크톱 서버 조사는 서브에이전트가 맡았다.
- 대상 작업: Task Master `C:\DEV\VoiceNote` 태그 `master`의 5번(프로젝트 제거·단순화), 9번(설정 화면·저장 위치), 6번(Windows 마이크 권한)

- 적용 범위: Windows 앱(`desktop`)과 Android 앱(`mobile\안드로이드`) 둘 다

## 한눈에 보기

앱을 열면 프로젝트를 고르거나 만들 필요 없이 바로 회의를 시작할 수 있게 바꾼다. 처음에 설정에서 OpenAI API 키만 한 번 넣으면, 이후에는 '회의 시작'을 눌러 녹음하고 '회의 종료'를 누르면 전사와 정리가 이어진다. 회의명과 동의 체크는 더 이상 시작을 막지 않는다.

지금까지 쌓인 회의 기록은 옮기거나 지우지 않는다. 옛 `프로젝트-01~03` 폴더를 그대로 둔 채, 왼쪽 '지난 회의' 목록 하나에 새 회의와 함께 보여 준다. 옛 기록을 열고, 원음을 듣고, 다시 분석하는 일도 그 기록이 원래 있던 폴더에서 처리한다.

흩어져 있던 AI 설정·설정 내보내기·설정 불러오기는 새 '설정' 화면 하나로 모은다. 같은 화면에 '내 형식' 편집과 저장 위치(오디오·전사문·요약본을 사본으로 저장할 폴더)도 둔다.

요약 품질은 프로젝트 배경 대신 사람이 결과를 읽고 매기는 평가로 보완한다. 요약을 읽고 별 1~5개와 한 줄 의견을 남기면, 그 의견을 반영해 요약만 다시 만들 수 있다. 전사는 다시 하지 않으므로 요약 요금만 추가로 든다. 한 회의에 결과가 여러 개 생기므로, 지난 회의 목록에는 최신 결과를 보여 주고 결과 창에서 앞선 결과와 그 평가를 다시 열 수 있게 한다.

이 설계에서 아직 확인하지 못한 것도 있다. Android 폴더 저장은 기기·저장소 앱마다 파일 이름 처리가 다를 수 있다. 실제 휴대폰에서의 동작은 사용자가 설치해 써 보기 전에는 확정할 수 없다. 자세한 내용은 맨 뒤 '아직 모르는 것과 위험'에 적었다.

## 바뀌는 사용 흐름

지금 Windows 앱은 프로젝트를 고르고, '회의 준비'에서 프로젝트 이름과 회의명을 적고, 동의 두 개를 체크해야 '회의 시작'이 눌린다. Android 앱은 회의명이 이미 선택 입력이지만 프로젝트 이름과 동의 두 개가 필요하다. 바뀐 뒤에는 키를 등록한 기본 상태라면 준비 절차 없이 '회의 시작'이 바로 눌린다. 진행 중인 회의가 있거나 날짜·메모 길이가 잘못된 경우처럼 지금도 있는 입력 검사는 그대로 막는다. 회의명·참석자·메모는 적고 싶을 때만 '회의 준비'를 펼쳐 적는다.

회의를 마치는 흐름은 지금과 같다. '회의 종료'를 누르면 음성을 먼저 저장하고, 전사와 정리가 이어지고, 결과가 지난 회의 목록에 남는다. 달라지는 점은 두 가지다. 결과가 저장되면 설정에서 고른 폴더에 사본이 함께 저장된다. 결과 화면에서 평가를 남기고 의견을 반영해 다시 정리할 수 있다.

## 화면

### 왼쪽 목록

'프로젝트' 구역과 그 아래의 '설정 내보내기·불러오기' 버튼을 없애고, '지난 회의' 목록 하나만 남긴다. 목록에는 새 회의와 옛 프로젝트 기록이 날짜가 최근인 순서로 섞여 나온다.

항목 모양은 지금처럼 `날짜 · N차 · 제목`과 상태(회의록 완료, 분석 대기 등)를 보여 준다. 여기에 두 가지를 더한다. 옛 프로젝트 기록에는 "이전 프로젝트: 홈페이지 개편"처럼 그때 프로젝트 이름을 작게 붙인다. 평가를 남긴 결과에는 별 개수를 붙인다. 회의명 없이 녹음만 끝난 기록은 "제목 미정 회의"로 보인다.

옛 기록 파일 하나가 손상돼 읽히지 않아도 목록 전체가 실패하지 않게 한다. 읽은 기록은 그대로 보여 주고, 목록 위에 "읽지 못한 기록 N개"만 알린다. Android는 지금 기록 하나가 깨지면 목록 전체가 실패할 수 있는 구조라서(Codex 조사) 이번에 함께 고친다.

도구 구역의 '현재 화면 비우기'와 '도구 종료'는 남긴다. '회의자료 폴더 열기'는 설정 화면으로 옮긴다.

### 상단 '설정' 버튼과 설정 화면

상단의 'AI 설정' 버튼을 '설정'으로 바꾼다. 버튼 옆의 상태 표시(키 필요, 모델 이름 등)는 그대로 둔다. 상단의 '현재 프로젝트' 표시는 없앤다.

설정 화면은 다섯 구역이다.

1. **AI 연결**: API 키 등록·삭제와 '이 PC에 키 저장', 요약 모델 선택. 지금 AI 설정 창의 내용을 그대로 옮긴다.
2. **출력 형식**: '기본 출력 형식' 선택과 '내 형식' 편집(이름, 넣을 항목과 순서, AI에게 줄 추가 지시, 저장·삭제, 예시 미리보기). 내 형식 편집은 지금 회의 준비 안에 있던 것을 그대로 옮긴다. 기본 출력 형식을 '내 형식'으로 정했는데 저장된 내 형식이 없으면(삭제했거나 설정 파일에 없을 때) 새 회의는 회의록 형식으로 시작한다.
3. **저장 위치**: 오디오·전사문·요약본 폴더를 각각 고른다. 각 줄에 지금 고른 폴더, '폴더 고르기', '사용 안 함' 버튼이 있다. 아래에 "앱 안 기록은 그대로 두고, 분석이 끝나면 고른 폴더에 사본을 씁니다. 요약본은 .md와 .txt 두 파일로 저장합니다."를 적는다.
4. **설정 파일**: '설정 내보내기'와 '설정 불러오기'. 불러오기를 누르면 지금처럼 바뀔 내용을 먼저 보여 주고 확인을 받는다.
5. **회의자료 폴더 열기**: Windows에만 둔다. Android는 앱 내부 폴더를 사용자가 직접 열 수 없어 이 구역이 없다.

녹음·분석·저장 중에는 설정을 바꿀 수 없게 잠근다. Windows는 지금도 그렇고, Android는 지금 진행 중에도 요약 모델을 바꿀 수 있어서 이번에 함께 잠근다.

### 회의 준비와 시작

'회의 준비'를 펼치면 다음만 남는다.

- 회의명: 선택. 빈칸 안내 "비워 두면 AI가 회의 내용을 보고 정합니다"
- 회의 날짜: 기본값 오늘
- 출력 형식과 '예시 보기': 예시는 보기만 한다. '내 형식'을 골랐는데 저장된 내 형식이 없으면 "설정 › 출력 형식에서 내 형식을 먼저 만드세요"와 설정 화면을 여는 버튼을 보여 준다.
- 참석자
- 상세 회의내용: 이번 회의의 안건·배경 메모. 요약할 때 참고 자료로만 보낸다(지금과 같음).
- 버튼: '마이크 음량 100% 설정'(Windows), '준비 내용 접기'

프로젝트 이름, '프로젝트 설명과 회의 정리 기준(프리셋)', '프리셋 저장', '프로젝트 삭제'는 없앤다.

'회의 시작'을 막는 조건에서 없애는 것은 프로젝트 이름, 회의명(Windows), 동의 체크 두 개뿐이다. 나머지 검사는 그대로 둔다. 남는 조건은 다음과 같다.

- 진행 중인 녹음·분석·저장이 있거나, 마이크 허가·파일 선택이 겹칠 때
- 지난 회의가 열려 있을 때('회의 준비'로 새 회의를 시작하라고 안내)
- 분석할 수 있는 키가 없을 때, 요약 모델을 다시 골라야 할 때
- 날짜 형식이 잘못됐거나 상세 회의내용이 4,000자를 넘을 때
- 내 형식을 골랐는데 저장된 내 형식이 없을 때

시작 버튼 아래에 "녹음 전에 참석자에게 녹음과 AI 분석(OpenAI 전송)을 알려 주세요." 한 줄을 늘 보여 준다. 누를 것은 없다.

### 결과 화면: 평가와 의견 반영 다시 정리

결과 창의 '정리본' 탭 아래에 '이 요약 평가' 구역을 둔다.

- 별 1~5개: 누르지 않아도 된다(선택).
- 의견: 한 줄 이상 적을 수 있는 칸, 1,000자까지. 예시 안내 "예) 담당자가 틀렸어요. 견적 검토는 이대리가 맡기로 했습니다." 다시 정리할 때 AI는 앞선 결과를 보지 않고 전사를 다시 읽는다. 그래서 '두 번째 항목'처럼 위치로 가리키기보다 무엇이 어떻게 틀렸는지 적도록 안내한다.
- '평가 저장': 별점과 의견을 저장한다. 요금이 들지 않는다.
- '의견 반영해 다시 정리': 의견 칸에 글이 있을 때만 눌린다. 버튼 옆에 "요약 요금이 추가로 듭니다. 긴 회의는 여러 번 나눠 요청할 수 있습니다."를 적는다.

다시 정리는 저장된 전체 전사를 그대로 쓰고 요약만 다시 요청한다. 저장된 전사가 없거나 읽히지 않으면 자동으로 다시 전사하지 않고, "저장된 전사가 없어 의견을 반영할 수 없습니다"라고 알린 뒤 멈춘다. 새 결과는 새 결과로 따로 저장된다. 지난 회의 목록에는 지금처럼 녹음마다 최신 결과 하나만 보인다. 결과 창 위쪽의 '결과 버전' 목록에서 앞선 결과와 그 평가를 다시 열 수 있다. 의견을 반영해 만든 결과에는 "의견 반영본"이라고 표시한다.

같은 결과 창에 '고른 폴더에 다시 저장' 버튼을 둔다. 사본 저장이 실패했을 때 다시 시도하거나, 옛 회의를 새로 고른 폴더로 내보낼 때 쓴다. 저장 위치를 하나도 고르지 않았으면 이 버튼 대신 "설정에서 저장 위치를 고르면 사본을 저장할 수 있습니다"를 보여 준다.

### Android 화면

Android도 같은 구성으로 바꾼다. 차이는 세 가지다. 설정 화면에 '회의자료 폴더 열기'가 없다. Android는 이미 회의명이 선택 입력이라(비우면 "회의") 그 부분은 바꿀 것이 없다. 저장 위치의 '폴더 고르기'는 Android 시스템 폴더 선택 화면을 띄운다.

## 저장 구조

### 보관함

회의 기록이 들어 있는 폴더를 '보관함'이라고 부른다. 보관함은 네 가지다.

| 보관함 이름(내부 표기) | 실제 폴더 | 용도 |
|---|---|---|
| 기본(`main`) | `회의자료\회의기록` | 새 회의는 모두 여기에 쌓는다 |
| 옛 1번(`p1`) | `회의자료\프로젝트-01` | 읽기·열기·다시 분석만. 새 녹음은 만들지 않는다 |
| 옛 2번(`p2`) | `회의자료\프로젝트-02` | 위와 같음 |
| 옛 3번(`p3`) | `회의자료\프로젝트-03` | 위와 같음 |

지난 회의 목록의 모든 항목은 자기 보관함 이름을 함께 가진다. 회의를 열고, 원음을 읽고, 전사를 저장하고, 다시 분석한 결과를 저장하고, 평가를 저장하고, 사본을 쓰는 모든 동작은 이 보관함 이름으로 폴더를 찾는다. 지금처럼 "현재 고른 프로젝트 번호"로 폴더를 짐작하지 않는다. 옛 기록을 다시 분석하면 새 결과도 그 옛 보관함에 저장한다. 원음과 같은 폴더에 있어야 기존 연결(녹음 id)이 그대로 맞기 때문이다.

옛 폴더 안의 `설정.json`(프로젝트 프리셋)은 지우지 않지만 더 읽지 않는다. 4~9번 폴더는 지금처럼 건드리지 않는다.

### 파일 배치

Windows는 보관함 폴더 안의 파일 이름 규칙을 지금과 같게 쓴다(`녹음-<id>.json`, `원음-<id>-NNN.webm`, `전사-<id>.txt`, `회의-<id>.json`, `회의-<id>.md`, `<날짜>-<NN>차-<제목>-<id8>-전사.txt` 등). 새로 생기는 파일은 평가 파일 `평가-<결과id>.json`과 사본 기록 파일(`사본기록-<결과id>.json`, `사본기록-원음-<녹음id>.json`)이다.

Android도 보관함 아래 회의마다 `<UUID>` 폴더를 두는 지금 구조를 그대로 쓴다. 새로 생기는 파일은 회의 폴더 안의 `결과-<결과id>.json`, `평가-<결과id>.json`, `사본기록-<결과id>.json`, `사본기록-원음.json`과 기본 보관함의 `작성중.json`이다. 결과 id는 아래 '결과 모델'에서 정한다.

### 결과 모델

회의 하나(녹음 하나)에는 결과가 여러 개 생길 수 있다. 처음 분석한 결과, 실패 뒤 다시 분석한 결과, 의견을 반영해 다시 정리한 결과다. 그래서 회의 id와 결과 id를 구분한다.

| | Windows | Android |
|---|---|---|
| 회의 id | 녹음 id(`녹음-<id>.json`과 원음 파일) | 회의 UUID 폴더 이름 |
| 결과 id | 결과 기록 id(`회의-<결과id>.json`) | 결과를 저장한 밀리초 시각 |

Windows는 지금도 결과마다 `회의-<결과id>.json`을 따로 남기고, 한 번 저장한 결과는 고치지 않는다. 바뀌는 것은 앞선 결과를 화면에서 다시 열 수 있게 하는 것뿐이다. 지난 회의 목록은 지금처럼 녹음마다 최신 결과 하나를 보여 주고, 결과 창의 '결과 버전' 목록이 같은 녹음의 결과를 저장 시각 순서로 보여 준다.

Android는 지금 회의마다 회의 정보 하나와 최신 요약(`요약.json`, `회의록.txt`)만 갱신하고, 앞선 요약은 본문만 `요약-<시각>.json`에 남긴다. 그래서 앞선 결과의 제목·형식·반영한 의견은 남지 않는다. 1.3.0부터는 결과를 저장할 때마다 `결과-<결과id>.json`에 제목·날짜·출력 형식·내 형식·반영한 의견·요약 본문·사용량을 함께 남긴다. 최신 결과를 가리키는 지금 파일(`회의정보.json`, `요약.json`, `회의록.txt`)도 그대로 갱신해 기존 화면과 공유가 계속 동작하게 한다. 1.2.0 이전에 생긴 `요약-<시각>.json`은 지우지 않지만, 제목·형식 정보가 없어 '결과 버전' 목록에는 넣지 않는다. 옛 회의의 최신 결과는 지금처럼 열린다.

평가, 사본 저장, 의견 반영은 모두 특정 결과 id를 대상으로 한다.

### 기록 안의 값

새 기록에는 프로젝트 번호(`slot`)를 넣지 않고 보관함 이름(`location`)을 넣는다. 새 회의는 `location: "main"`이고 프로젝트 이름(`projectName`)도 없다. 옛 기록은 파일을 고치지 않으므로 `slot`과 `projectName`이 그대로 남는다. 목록에 "이전 프로젝트: …"를 붙일 때 이 값을 쓴다. 옛 보관함의 회의를 다시 분석해 만든 새 결과에는 그 보관함 이름(`p1` 등)을 넣고, 그 녹음의 옛 프로젝트 이름을 옮겨 적어 꼬리표가 그대로 보이게 한다. Windows는 기록을 읽을 때 지금 "파일 안의 slot과 폴더 번호가 같은지" 검사하는데, 이것을 "보관함 이름과 폴더가 맞는지" 검사로 바꾼다. 옛 기록은 `slot` 값으로 옛 보관함을 확인한다. Android는 지금 이런 검사가 없으므로 같은 검사를 새로 넣는다.

Windows 회의록 Markdown 머리글의 "프로젝트: …" 줄은 `projectName`이 있는 옛 기록에만 쓴다.

### 차수

날짜별 차수(1차, 2차…)는 지금처럼 보관함 하나 안에서 센다. 새 회의는 기본 보관함 안에서 날짜별로 센다. 옛 기록의 차수는 저장된 값을 그대로 쓴다. 그래서 같은 날짜에 옛 프로젝트 기록과 새 회의가 둘 다 "1차"일 수 있다. 옛 기록에는 프로젝트 이름 꼬리표가 붙어 있어 구분된다.

### 회의명이 빈 경우

Windows 서버는 지금 녹음 정보를 만들 때와 결과를 저장할 때 회의명을 필수로 검사한다. 녹음 정보는 회의명이 비어 있어도 만들 수 있게 바꾼다. 녹음 단계에서는 아직 AI 제목이 없기 때문이다. 결과를 저장할 때는 AI가 정한 제목을 쓰고, 그것도 비어 있으면 "회의"를 쓴다.

### Android 작성 중 메모

Android는 프로젝트마다 `작성중.json`(회의명·날짜·참석자·메모)을 따로 저장해 왔다. 앞으로는 기본 보관함의 `작성중.json` 하나만 쓴다.

옛 메모는 처음 한 번만 가져온다. 옛 세 메모 중 가장 최근에 바뀐 것의 내용을 가져오고, 가져왔다는 사실을 앱 설정에 따로 기억한다. 녹음을 시작하면 새 메모 파일이 지워지는데, 파일이 없다는 이유만으로 다시 가져오면 오래된 메모가 되살아나기 때문이다. 가장 최근 메모가 손상됐으면 그다음 메모를 쓰고, 쓸 수 있는 것이 없으면 빈 메모로 시작한다. 옛 메모 파일은 지우지 않는다.

## 요약 요청

### 입력에서 빠지는 것과 남는 것

요약 요청에서 프로젝트 배경(`context`) 칸과 "context는 사전 참고 정보와 정리 기준입니다…" 지시문을 뺀다. 지금도 프로젝트 이름은 AI에 보내지 않으므로 그 밖에 뺄 것은 없다.

남는 입력은 회의명, 날짜, 참석자, 전사, 상세 회의내용(있을 때만), 앞 구간 결과(긴 회의를 나눌 때만), 출력 형식, 내 형식이다. 옛 프로젝트 기록을 다시 분석할 때도 그 기록에 저장된 옛 프로젝트 배경은 더 보내지 않는다.

### 의견 반영 지시

다시 정리할 때만 요청에 의견(`feedback`, 1,000자 이하)을 넣고, 다음 뜻의 지시를 더한다.

> feedback은 사용자가 앞선 정리본을 읽고 남긴 검토 의견입니다. 의견이 가리키는 내용을 전사에서 다시 확인해 고쳐 정리하세요. 의견에 있더라도 전사에 없는 발언·결정·담당자·기한은 만들지 마세요. 의견이 전사와 맞지 않으면 전사를 따르고 '확인 필요'로 남기세요.

긴 회의를 여러 구간으로 나눠 보낼 때는 모든 구간 요청에 같은 의견을 넣는다. 구간을 잇는 방식(앞 구간 결과를 다음 요청에 붙이는 것)은 바꾸지 않는다.

### Android가 같은 요청을 보내게 하기

Android는 요약 지시문을 직접 갖고 있지 않고, 빌드할 때 Windows 서버 코드에서 뽑아 쓴다(`요약계약추출.cjs`). 이 추출기는 지금 입력 칸을 `context, date, participants, title, transcript`로 고정 검사하므로 함께 고친다. 일반 요약의 입력은 `date, participants, title, transcript`(필요할 때 `notes`, `previousMinutes`)이고, 의견 반영 요약은 여기에 `feedback`이 더해진다. 일반 요약에는 `feedback` 칸이 아예 없다. 추출기는 두 경우를 따로 뽑고 따로 검사한다. 같은 입력이면 두 앱이 같은 요청을 보낸다는 기존 시험은 그대로 유지한다.

Android는 구간별 중간 요약을 캐시해 같은 입력이면 다시 쓰는데, 지금은 지시문이 바뀌어도 옛 캐시를 다시 쓸 수 있다. 캐시를 찾는 기준에 지시문 내용의 해시와 의견을 넣어, 지시문을 고치거나 의견을 반영할 때 옛 결과가 재사용되지 않게 한다.

## 평가 저장과 다시 정리

평가는 AI 결과 파일을 고치지 않고 별도 파일에 저장한다. 결과는 한 번 저장하면 바꾸지 않는다는 원칙을 지키기 위해서다. Windows는 지금도 그렇고, Android는 위 '결과 모델'부터 같아진다.

```json
{ "version": 1, "stars": 4, "comment": "담당자가 틀렸어요…", "savedAt": "2026-10-23T12:00:00.000Z" }
```

- `stars`는 1~5 정수이거나 `null`(별점 없이 의견만)이다. `comment`는 1,000자 이하다. 둘 다 비어 있으면 저장하지 않는다.
- 같은 결과에 다시 저장하면 그 결과의 평가 파일을 바꾼다. 다른 결과의 평가는 건드리지 않는다.
- 지난 회의 목록은 결과마다 평가 파일이 있는지 읽어 별 개수를 붙인다.

다시 정리 흐름은 다음과 같다. 사용자가 의견을 적고 '의견 반영해 다시 정리'를 누르면 먼저 평가를 저장한다. 그다음 저장된 전체 전사(Windows는 결과 기록의 전사, Android는 회의 폴더의 `전사.txt`)와 지금 결과의 출력 형식으로 요약만 다시 요청한다. 이 경로는 원음을 다시 전사하지 않는다는 점에서 실패 복구용 '다시 분석'과 다르다. Android는 지금 분석이 원음별 전사 파일이 없으면 다시 전사하므로, 이 경로를 따로 만든다. 새 결과를 저장할 때 반영한 의견(`feedback`)을 함께 남기고, 결과 화면은 새 결과로 바뀌며 "의견 반영본" 표시가 붙는다. 요약 요청이 실패하면 평가는 저장된 채로 남고 앞선 결과도 그대로다.

키가 없으면 다시 정리 대신 설정에서 키를 등록하라고 안내한다. 녹음·분석·저장 중에는 평가 저장과 다시 정리를 잠근다.

## 고른 폴더에 사본 저장

### 설정 값

설정에는 오디오·전사문·요약본 폴더가 각각 하나씩 있다. 비어 있으면 그 종류는 사본을 쓰지 않는다. 세 종류를 같은 폴더로 골라도 된다.

### 폴더 고르기

**Windows**: '폴더 고르기'를 누르면 화면이 Windows 창 쪽에 폴더 선택을 요청하고, 창이 Windows 폴더 선택 대화상자를 띄운다. 사용자가 폴더를 고르면 서버가 그 폴더가 실제로 있고 파일을 쓸 수 있는지 시험 파일을 만들었다 지워 확인한 뒤 저장한다. 쓸 수 없으면 저장하지 않고 이유를 보여 준다.

**Android**: Android 시스템 폴더 선택 화면을 띄우고, 사용자가 고른 폴더에 대해 앱을 다시 켜도 유지되는 읽기·쓰기 권한을 받는다. 화면에는 폴더 이름을 보여 준다. 받은 권한이 나중에 끊기면(폴더 삭제, 권한 회수 등) 다음 사본 저장 때 실패로 알리고 다시 고르라고 안내한다. 세 종류가 같은 폴더를 쓰면 권한도 하나를 같이 쓴다. 한 종류를 '사용 안 함'으로 바꿀 때 다른 종류가 그 폴더를 계속 쓰면 권한을 놓지 않는다. Android 11부터는 저장소 맨 위, `Download` 맨 위, `Android/data` 같은 폴더는 고를 수 없게 막혀 있다. 이것은 Android 자체 제한이다.

### 언제, 무엇을, 어떤 이름으로

분석 결과가 저장되면 이어서 사본을 쓴다. Windows는 서버가 결과를 저장한 직후에, Android는 분석이 끝나 요약이 저장된 직후에 쓴다. Windows는 결과 파일 이름에 이미 쓰는 `<날짜>-<NN>차-<제목>-<결과id 앞 8자>`를 앞부분으로 쓴다. Android는 `<날짜>-<NN>차-<제목>-<결과id>`를 쓴다. Android 결과 id는 밀리초 시각이라 앞 8자리만 쓰면 다른 회의와 겹칠 수 있어 전부 쓴다. 지금 Android 공유 파일 이름에도 시각이 붙지만, 그것은 공유 버튼을 누른 시각이라 결과를 가리키지 않는다. 아래 표는 Windows 기준이다.

| 종류 | 파일 | 내용 |
|---|---|---|
| 전사문 | `…-<결과id8>-전사.txt` | 전사 원문 |
| 요약본 | `…-<결과id8>-요약.md` | 제목·날짜·참석자와 절 구조를 갖춘 Markdown |
| 요약본 | `…-<결과id8>-요약.txt` | 같은 내용을 기호 없이 읽기 쉽게 쓴 텍스트 |
| 오디오 | `…-<녹음id8>-원음-01.<원본 확장자>` | 녹음 원본 그대로. Windows는 녹음된 형식에 따라 `.webm`·`.m4a`·`.wav`, Android는 `.m4a`. 파일이 여러 개면 01, 02… |

요약본 두 파일의 모양은 두 앱이 같게 만든다. 지금 Windows는 Markdown 모양만(화면의 '텍스트 저장'도 같은 Markdown 본문), Android는 기호 없는 텍스트만 만들 줄 안다. 그래서 Windows에는 텍스트 변환기를, Android에는 Markdown 변환기를 하나씩 새로 만든다. 두 파일 모두 구조화된 요약 자료에서 각각 만들고, Markdown 기호를 지워서 텍스트를 만들지 않는다. 네 출력 형식별 공통 예시 자료를 두고 두 앱의 결과가 같은지 시험한다.

오디오는 결과가 아니라 녹음에 딸린 것이므로 이름에 녹음 id를 넣는다(Android는 회의 id 앞 8자). 전사문·요약본은 결과 id가 이름에 들어가 다시 분석할 때마다 새 파일이 생긴다.

### 사본 기록

어떤 사본을 이미 썼는지는 파일 이름으로 짐작하지 않고 '사본 기록' 파일에 남긴다. 결과마다 `사본기록-<결과id>.json`에 전사문·요약본(.md)·요약본(.txt) 각각의 대상 폴더, 실제 저장한 이름(Android는 문서 주소), 성공 여부를 적는다. 원음은 녹음마다(Windows `사본기록-원음-<녹음id>.json`, Android 회의 폴더의 `사본기록-원음.json`) 대상 폴더와 순번별 저장 결과를 적는다. 이 기록으로 다음 규칙을 지킨다.

- 다시 저장할 때는 지금 설정된 폴더 기준으로, 아직 성공하지 않았거나 저장한 파일이 사라진 것만 쓴다. `.md`는 성공하고 `.txt`만 실패했다면 `.txt`만 다시 쓴다.
- 원음은 녹음 id와 순번으로 이미 쓴 것을 판별한다. 다시 분석해 제목이 바뀌어도 같은 원음을 또 복사하지 않는다.
- 폴더를 바꾼 뒤 다시 저장하면 새 폴더 기준으로 아직 없는 것을 쓴다. 옛 폴더의 사본은 지우지 않는다.
- 쓰려는 이름에 사본 기록에 없는 다른 파일이 이미 있으면 덮어쓰지 않고 이름 끝에 `(2)`, `(3)`을 붙인다.
- 쓰다가 실패한 반쪽 파일은 남기지 않는다. Windows는 임시 이름으로 쓴 뒤 이름을 바꾸고, Android는 만들던 문서를 지운다.

### 실패와 다시 저장

사본 저장이 실패해도 회의 결과 저장은 성공으로 둔다. 원본은 앱 안에 이미 안전하게 저장돼 있기 때문이다. 대신 결과 화면과 상태 줄에 "고른 폴더에 저장하지 못했습니다: <이유>. 설정에서 폴더를 확인한 뒤 '고른 폴더에 다시 저장'을 누르세요."를 보여 준다. 세 종류 중 일부만 실패하면 실패한 종류만 알린다.

## 설정 파일 2판

### 담는 내용

```json
{
  "format": "voicenote-settings",
  "version": 2,
  "summaryModel": "gpt-6.1-sol",
  "defaultOutputFormat": "meeting",
  "customFormat": { "name": "주간 보고", "sections": [{ "key": "overview", "title": "요약" }], "instruction": "" },
  "storage": { "audio": "D:\\회의\\원음", "transcript": "D:\\회의\\전사", "summary": "D:\\회의\\요약" }
}
```

- `customFormat`은 저장된 내 형식이 없으면 `null`이다.
- `storage`는 Windows가 내보낼 때만 넣는다. Android 폴더 권한은 그 기기 안에서만 유효해 다른 기기로 옮길 수 없으므로 Android 파일에는 넣지 않는다.
- API 키, 체험 기록, 회의 기록, 녹음은 넣지 않는다(지금과 같음).
- 크기 상한(128KiB), UTF-8 검사, 허용하지 않는 칸이 있으면 거절하는 엄격한 검사는 지금 1판과 같은 수준으로 유지한다.

### 내보내기와 불러오기

내보내기는 지금 저장된 설정을 `<오늘>-VoiceNote-설정.json`으로 저장한다.

불러오기는 파일을 고르면 먼저 바뀔 내용을 보여 준다(요약 모델, 기본 출력 형식, 내 형식 이름, 저장 위치 세 개). 확인을 누르면 파일에 든 값으로 바꾼다.

- 저장 위치는 그 PC에 폴더가 있고 쓸 수 있을 때만 적용하고, 아니면 그 줄만 건너뛰고 미리보기에 "이 PC에 없는 폴더라 적용하지 않습니다"라고 표시한다.
- 파일에 `storage`가 아예 없으면(Android에서 만든 파일 등) 지금 저장 위치를 그대로 둔다. `storage` 안의 어떤 종류가 빈 값이면 그 종류는 '사용 안 함'으로 바꾼다.
- Android는 `storage`가 있어도 적용하지 않는다.
- 파일의 요약 모델이 지금 앱 목록에 없으면 그 값은 적용하지 않고 알린다.
- 여러 값을 바꾸다가 하나라도 저장하지 못하면 모두 이전 값으로 되돌리고 실패를 알린다. 요약 모델·저장 위치와 내 형식은 서로 다른 파일에 저장되므로, 바꾸기 전 값을 보관해 두었다가 되돌린다.

### 이전 1판 파일

`voicenote-project-settings` 1판 파일(프로젝트 설정)을 고르면 "이전 버전의 프로젝트 설정 파일입니다. 프로젝트 기능이 없어져 불러올 수 없습니다."를 보여 주고 아무것도 바꾸지 않는다. 1판에는 새 설정에 해당하는 값이 없기 때문이다.

### Android 공용 코드

Android의 내 형식 검증(`CustomFormat.java`)은 설정 파일 해석기(`SettingsExchange`)의 공용 부분을 빌려 쓴다. 그래서 1판 프로젝트 교환 코드를 없앨 때 이 공용 해석 부분은 남기거나 따로 떼어 둔다.

## Windows 마이크 권한과 자체 검사

Windows 앱의 권한 처리(`프로그램.cs`)에서, 앱 자신의 로컬 화면이 마이크를 요청하면 묻지 않고 허용한다. 다른 주소나 다른 권한 요청은 지금처럼 거부한다. Windows 개인정보 설정에서 마이크를 꺼 두었다면 그 설정이 여전히 우선한다.

Windows 앱의 자체 검사 기능은 화면에 프로젝트 버튼이 9개 있는지를 기다리는데, 지금 화면은 버튼을 1개만 그려 이미 맞지 않을 가능성이 높다. 새 화면에는 프로젝트 버튼이 없으므로, '설정' 버튼과 지난 회의 목록이 있고 화면 상태 함수가 동작하는지를 확인하도록 바꾼다. 가상 마이크 녹음 확인은 그대로 둔다.

## 검증 계획

GitHub Actions가 없으므로 모든 시험은 로컬에서 돌린다. 시험은 지금 시험 파일을 새 구조에 맞게 고치고, 아래 항목을 새로 넣는다.

1. **옛 기록 합쳐 보기**: 옛 `프로젝트-01~03` 구조를 흉내 낸 시험 자료와 새 회의를 함께 넣고, 목록·열기·원음 읽기·다시 분석 저장·평가·사본 저장이 각자 원래 보관함에서 처리되는지 확인한다. 손상된 옛 기록 하나가 섞여도 나머지가 보이는지 확인한다. Windows와 Android 둘 다 한다.
2. **결과 버전**: 같은 회의를 다시 분석·의견 반영한 뒤, 목록에는 최신 결과가 보이고 '결과 버전'에서 앞선 결과를 열면 그때의 본문·형식·평가가 그대로 나오는지 확인한다. Android는 1.2.0 이전 회의(결과 파일 없음)도 최신 결과가 지금처럼 열리는지 함께 본다.
3. **요약 요청 형식**: 일반 요약에는 `context`와 `feedback`이 없고 의견 반영 요약에만 `feedback`이 들어가는지, 지시문이 맞는지, Android가 같은 입력에 같은 요청을 만드는지(두 경우 각각), Android 캐시가 지시문·의견 변경에 반응하는지 확인한다.
4. **의견 반영 경로**: 저장된 전사로 요약만 다시 하고 전사 요청이 나가지 않는지, 저장된 전사가 없으면 멈추는지, 요약이 실패해도 평가와 앞선 결과가 남는지 확인한다.
5. **설정 파일 2판**: 왕복(내보내고 다시 불러오기), 엄격한 거절 사례, 1판 거절, 저장 위치가 없는 PC에서의 건너뛰기, `storage`가 없는 파일과 빈 값인 파일의 차이, 중간 실패 때 모두 되돌리기, Windows와 Android 파일 호환을 확인한다.
6. **사본 저장**: 임시 폴더를 저장 위치로 정하고 파일 이름·내용(`.md`, `.txt`, 전사, 원음)을 확인한다. 원음 중복 건너뛰기, 이름 충돌 `(2)`, `.md`만 성공한 뒤 다시 저장, 다시 분석으로 제목이 바뀐 경우, 세 종류를 같은 폴더에 저장, 폴더를 바꾼 뒤 다시 저장, 쓰기 실패 때 회의 저장은 성공하는지도 본다. Android는 폴더 쓰기를 파일 기반 대체물로 시험하고, 실제 시스템 폴더 선택과 같은 폴더 권한 공유는 에뮬레이터에서 확인한다.
7. **시작 조건과 초안**: 키를 등록한 기본 상태에서 시작 버튼이 바로 눌리는지, 안내 한 줄이 보이는지, 진행 중·날짜·메모 길이 검사는 그대로 막는지 확인한다. Android 옛 메모를 한 번만 가져오고, 녹음 뒤 다시 실행해도 되살아나지 않는지 확인한다.
8. **화면 검사**: 헤드리스 Chrome으로 Windows 화면과 Android 화면(모의 앱 연결)을 여러 폭에서 캡처해 설정 화면·목록·회의 준비·결과 평가 구역·결과 버전의 배치와 넘침을 직접 열어 본다.
9. **실제 Windows 창**: 사용자 승인에 따라 마지막에 한 번 띄운다. 실제 회의자료는 건드리지 않고 임시 자료 폴더를 쓰며, 옛 기록 합쳐 보기는 기존 회의자료를 임시 폴더에 복사해 확인한다. 폴더 선택 대화상자, 마이크 자동 허용, 자체 검사를 확인한다.
10. **Android 에뮬레이터**: 화면 없이(`-no-window`) 켜서 기기 시험(AndroidChecks)을 돌린다. 시스템 폴더 선택은 자동 조작(`adb`, 화면 구조 읽기)으로 고르고 권한 유지·사본 쓰기를 확인한다.
11. **실제 OpenAI 호출(최대 6회)**: 이 PC에 저장된 키로, 지어낸 짧은 회의 글을 요약만 시킨다. 배경 없는 기본 요약, 의견 반영 다시 정리, 업무 정리 형식을 확인하고 남는 횟수는 문제가 생길 때만 쓴다. 키 값은 화면과 기록에 남기지 않는다.
12. **깨끗한 복제본 전체 시험**: 마지막 커밋을 새 폴더에 복제해 Windows·Android 시험 전체를 돌린다.

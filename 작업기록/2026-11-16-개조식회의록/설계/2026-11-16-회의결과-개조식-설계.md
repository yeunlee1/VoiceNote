## 왜 하는가

- 지금 결과는 2~4문장 문단이라 읽기 힘듦(사용자 원문)
- 지금 AI 지시가 일부러 문장형을 요구함
  - 회의록형 — "짧은 키워드 목록이 아니라 설명형 회의록", "points는 서로 연결되는 2~4문장의 문단, 글머리표나 키워드만 출력하지 마세요"
  - 핵심 요약형 — overview "3~6문장의 이어지는 문단", points "1~3개의 짧은 문단"
  - 업무 정리형 — task "한 문장", overview "2~4문장"
  - 결과 줄이기 — "완전한 문장으로"
- 화면·복사·파일 저장도 주제별 내용과 회의록형 합의된 방향을 문단으로 내보냄 → 지시만 바꾸면 목록 모양이 되지 않음

## 목표

- 새로 정리하는 회의 결과가 네 출력 형식(회의록·핵심 요약·업무 정리·내 형식) 모두 개조식임
- 결정 이유·조건·이견·미확정 표현은 지금처럼 빠짐없이 남되, 문단이 아니라 하위 항목으로 남음
- Windows와 휴대폰이 같은 저장 구조를 쓰고, 목록·하위 목록 모양으로 보이고 저장됨
- 이미 만든 회의는 파일을 고치지 않고 그대로 열림

## 하지 않을 것

- 이미 만든 회의 결과를 AI로 다시 정리하기(비용 발생, 사용자가 원하면 기존 '다시 분석'으로 함)
- 하위 항목 두 단계 이상
- 다음 할 일(actions)의 저장 구조 변경 — 지금처럼 할 일·담당·기한 한 줄
- 절(핵심 요약·주요 내용 등)의 순서와 제목 바꾸기 — 형식·앱마다 지금 순서·제목 그대로(사용자 결정 "지금 순서·제목 그대로")
- Windows와 휴대폰 사이에 이미 있는 절 제목 차이, Windows 위쪽·아래쪽 텍스트 저장의 기존 차이 통일
- 사람이 고친 할 일을 다시 분석 결과로 이어 붙이는 규칙 바꾸기
- 앱 버전 올리기·릴리즈(따로 허락받음)

## 실패로 볼 것

- 이유·조건이 빠진 키워드 나열이 됨(지금 지시가 지키는 품질을 잃음)
- 옛 회의가 열리지 않거나, 내용 일부가 잘리거나 사라져 보임
- 두 앱의 저장 구조나 목록·하위 목록 모양이 다름
- 글머리표가 두 번 붙음(AI가 넣은 기호 + 프로그램이 붙인 기호)
- 옛 회의를 열기만 했는데 저장 파일이 바뀜

## 만드는 방법

- 방법 1(채택) — 결과 저장 구조에 하위 항목 칸을 만들고 AI 응답 틀(JSON schema)로 강제
  - 모양이 늘 일정함, 화면·복사·파일이 같은 구조를 씀
  - 두 앱의 응답 틀·결과 읽기·화면·파일·줄이기·의견 반영·긴 회의 이어 붙이기·시험을 모두 고쳐야 함
- 방법 2(버림) — 구조는 그대로 두고 글 안의 "- " 줄을 하위 항목으로 보기
  - 작업은 작지만 AI가 규칙을 어겨도 막을 수 없음, 다른 기능이 모두 줄 규칙을 알아야 함

- 위 그림은 목록·하위 목록의 모양을 보이는 예시임, 절의 순서와 제목은 형식·앱마다 지금 것을 따름
- 하위 항목은 한 단계만
- 하위 항목을 쓰는 곳 — 핵심 요약(머리말 아래)·주요 내용·합의된 방향·미확정 사항
- 다음 할 일은 한 줄(할 일 · 담당 · 기한), 할 일 글도 짧은 꼴(「~하기」·명사형)
- 끝맺음 — 명사형이나 「~함」「~음」「~임」, 「~합니다」「~했다」와 여러 문장 문단 없음
- 글머리표 기호는 프로그램이 붙임, AI 글에는 기호를 넣지 않음

## 저장 구조

- 항목 하나 — `{ "text": 문자열, "details": 문자열 배열 }`
- 바뀌는 칸
  - `overview` — 문자열 → 항목 배열
    - 회의록형은 머리말 넷(전체 방향·주요 결정·다음 할 일·남은 쟁점)을 `text`로, 내용을 `details`로
  - `topics[].points` — 문자열 배열 → 항목 배열
  - `decisions` — 문자열 배열 → 항목 배열
  - `openQuestions` — 문자열 배열 → 항목 배열
- 그대로인 칸 — `suggestedTitle`, `actions`(`task`·`owner`·`due`)

## 두 가지 검사

- AI 응답 검사(새 구조만, 엄격) — `minutesJsonSchema`·`compactJsonSchema`(AI 응답 틀)와 그 결과 검사
  - `text` 1~1000자, `details` 0~8개 각 1~1000자
  - `overview` 최대 12개, 주제 최대 30개·주제마다 항목 최대 30개, `decisions`·`openQuestions` 최대 40개
  - 옛 구조(문자열)로 돌아온 응답은 응답 형식 오류
- 저장 결과 검사(옛 구조 또는 새 구조) — Windows 저장소(`회의보관.cjs`)가 읽고 쓸 때
  - 옛 구조는 지금 검사(`minutesSchema`)를 그대로 통과하면 됨(빈 문자열·2000자 문단·긴 overview 허용)
  - 새 구조는 위 AI 응답 검사와 같은 한도
  - 옛 결과를 새 한도로 바꿔 검사하지 않음 → 지금 열리는 옛 회의는 계속 열림
- 전체 응답 길이 한도(응답 JSON 64,000자, `AI_OUTPUT_LIMIT`)는 항목 한도와 따로 그대로 둠
  - `text`·`details` 키가 늘어 JSON이 길어지므로 한도 여유를 시험으로 확인

## 원본과 화면용 값의 경계

- 저장 원본(`minutes`)은 어디서도 바꾸지 않음
  - 저장소가 읽어 돌려주는 값, 결과 버전 파일, JSON 내보내기(`요약.json` 포함), 같은 회의 저장 재시도의 지문은 모두 원본 그대로
  - 옛 결과는 옛 구조 그대로 내보냄, 새 결과는 새 구조
- 새 구조로 바꾸는 것은 쓰는 쪽 바로 앞에서만 함
  - 화면 그리기(결과 화면·형식 예시·내 형식 미리보기)
  - 글 만들기(md·txt·복사·공유·사본·자동 보관 글·공유 ZIP의 정리본)
  - AI에 다시 보내는 결과(긴 회의 앞 구간, 결과 줄이기)
- 사람이 고친 할 일을 합치는 지금 경계(`exportDocument`·`appliedMinutes`)는 그대로, actions는 바꾸지 않음
- 같은 원본을 여러 번 바꿔도 결과가 같음(시험으로 확인)
- AI에 다시 보내는 입력(앞 구간 `previousMinutes`·줄이기 `minutes`)은 AI 응답 한도로 검사하지 않음(짝보고 3)
  - 저장 결과 검사(옛·새 허용)와 지금의 입력 직렬화 길이 제한(64,000자)만 적용한 뒤 새 구조로 바꿔 보냄
  - 허용된 긴 옛 문단·12줄 넘는 옛 overview가 다시 보낼 때 거절되지 않는지 시험

## 옛 결과 바꾸기 규칙

- 공통
  - 항목 글 앞뒤 공백을 떼고, 맨 앞의 글머리표 묶음(`-`·`•`·`·`·`*` 뒤에 공백, 여러 번 겹친 것 포함)을 떼어 냄
  - 비게 된 항목은 버림, 내용이 있는 글은 길이와 관계없이 자르지 않음
  - 공백만 있는 글도 빈 글로 봄
- `points`·`decisions`·`openQuestions` 문자열 — 문자열 하나를 `{ text: 문자열, details: [] }` 하나로
  - 문단 안의 줄바꿈은 그대로 두고 한 항목 안에서 줄을 바꿔 보임
- `overview` 문자열 — 줄마다 항목 하나
  - 알려진 머리말 넷(전체 방향·주요 결정·다음 할 일·남은 쟁점)으로 시작하는 `머리말 | 내용` 줄만 `{ text: 머리말, details: [내용] }`
    - 첫 ` | `에서만 나눔, 내용 안의 다른 ` | `는 그대로
    - 내용이 비면 `{ text: 머리말, details: [] }`(앞뒤 공백을 지워 `전체 방향 |`처럼 끝 구분자만 남은 줄 포함)
  - 다른 ` | ` 줄(예: `DB | API 연결 방식 검토`)과 그 밖의 줄은 `{ text: 줄, details: [] }`
  - 빈 줄과 기호만 있는 줄은 버림, 줄 수에 상한을 두지 않음
- 같은 규칙을 두 곳에 둠
  - JS — `출력형식.js`(휴대폰 `assets/formats.js`와 바이트가 같은 파일)
  - Java — 휴대폰 네이티브(문서·사본·길이 계산·줄이기가 씀)
  - JS와 Java가 같은 공통 예시로 같은 결과를 내는지 시험

## AI 응답 처리 순서

- JSON 읽기 → AI 응답 검사(엄격) → 일본어·중국어 글자 정리 → 빈 값 정리 → 저장
- 빈 값 정리 규칙(정리 뒤 비게 된 글)
  - 빈 `details` 글은 버림
  - `text`가 비고 `details`가 남으면 첫 `details`를 `text`로 올림
  - `text`와 `details`가 모두 비면 항목을 버림
  - 회의록형 핵심 요약 머리말은 내용이 비어도 머리말만 남김
- JS(`withoutForeignScript` 다음)와 Java(`Ai.java` 같은 자리)가 같은 공통 예시로 같은 결과

## AI 지시 바꾸기

- 네 형식 공통 개조식 규칙을 지시에 넣음
  - 항목 하나에 내용 하나, 짧은 끝맺음, 여러 문장 문단 금지
  - 이유·근거·조건·이견·영향은 `details`로
  - 글머리표 기호를 쓰지 않음
  - 지금의 사실 보존 규칙은 그대로(전사에 없는 결정·담당·기한 만들지 않음, 제안을 확정으로 바꾸지 않음, 모순 검토)
- 형식별
  - 회의록형 — 설명형 문단 요구와 글머리표 금지 문장을 개조식 규칙으로 바꿈, overview는 머리말 넷을 `text`로(내용이 없으면 "확정된 내용 없음"을 `details`로), 작성 예시를 개조식 예시로, decisions `text`는 「대상 — 합의한 행동」, 이유·적용 범위는 `details`
  - 핵심 요약형 — overview "3~6문장 문단" → 무엇을 왜 논의했고 결론·남은 쟁점이 무엇인지 3~6개 항목, points "1~3개 짧은 문단" → 1~5개 항목
  - 업무 정리형 — task "한 문장" → 결과물이 드러나는 짧은 한 줄, overview "2~4문장" → 2~4개 항목
  - 내 형식 — "overview가 목록에 없으면 한 문장으로만" → "항목 하나로만", 추가 지시가 개조식·사실 규칙과 부딪히면 그 규칙을 따름(`출력형식.js` `customInstruction`과 `CustomFormat.java`를 같이 고침)
- 다른 지시의 문장형 표현도 맞춤
  - 결과 줄이기 — "완전한 문장으로" → 개조식 유지, 항목·하위 항목 수부터 줄임, 이유·조건은 남김
  - 긴 회의 이어 붙이기 — "주제와 주제별 문단" → "주제와 주제별 항목"
  - 사람 표기 — "문장에 그 사람을 밝혀 쓰세요" → "항목에"
  - 의견 반영 지시는 그대로(형식 규칙은 위 지시가 맡음)
- 휴대폰은 빌드 때 서버 요청 본문을 그대로 가져가므로(`요약계약추출.cjs`) 서버를 고치고 다시 빌드하면 요청이 따라옴
  - 추출기의 모의 응답도 새 구조로 맞춤
  - 휴대폰 중간 결과 캐시는 지시 자산 지문을 키로 씀, 내 형식 지시만 바뀌는 경우도 캐시가 갈리는지 구현 때 확인

## 결과 줄이기

- 바꿀 수 있는 칸은 지금처럼 overview·topics뿐, 결정·할 일·미확정은 원문 그대로 되붙임
- 줄인 결과를 받아들이는 조건을 새 구조로 고침(Windows `서버.cjs`, 휴대폰 `Ai.java`)
  - 본문 글자 수(`text`+`details`)가 실제로 줄었을 때만
  - 원래 overview·topics가 있었는데 줄인 결과에서 비면 받지 않음(머리말만 남고 내용이 다 빈 경우 포함)
  - 받지 않으면 원래 결과 전체를 그대로 씀
- 길이 계산(`minutesLengths`·`compactTarget`, 휴대폰 `Ai.java`)이 `text`와 `details`를 함께 셈

## 화면

- Windows(`화면/app.js`)·휴대폰(`assets/app.js`) 결과 화면과 형식 예시·내 형식 미리보기
  - 핵심 요약·주요 내용·합의된 방향·미확정 사항을 목록으로, `details`는 안쪽 목록으로
  - 지금 문단(`p`)으로 그리는 곳 — Windows 1793·1795·1804·1809·1832·1843·1850행 근처, 휴대폰 519~525행 근처
  - 다음 할 일 화면(고치기·체크)은 그대로
- 형식 예시(`SAMPLE`)를 새 구조로 바꿈, 예시 설명(`DESCRIPTIONS`)의 "씁니다"는 화면 안내라 그대로
- 지원 폭 — Windows 창, 휴대폰 360·390·412, 긴 항목·빈 칸·옛 결과도 확인

## 복사·공유·파일 저장

- 목록 모양
  - 항목은 그 경로의 지금 목록 기호를 그대로 씀 — md·txt·휴대폰 복사는 `- 본문`, Windows 위쪽 복사·공유·텍스트 파일(`resultText`)은 지금처럼 `• 본문`
  - 하위 항목은 모든 경로에서 두 칸 들여 `  - 하위`
- 고칠 경로
  - Windows 위쪽 복사·공유·텍스트 파일(`resultText`)
  - Windows 아래쪽 '다른 형식으로 저장' md·txt(`lines`)와 JSON(`exportDocument`, 원본 그대로)
  - Windows 서버 문서(`회의문서.cjs` markdown·plainText) → 자동 보관(`회의보관.cjs`)·고른 폴더 사본(`사본저장.cjs`)이 씀
  - 휴대폰 문서(`MeetingDocument.java` md·txt) → 복사·정리본 공유·텍스트 저장·사본(`Copies.java`)·결과 버전 보조 파일(`Store.java`)이 씀
  - 휴대폰 전체 공유 ZIP(`MainActivity.java`의 정리본 txt, `요약.json`은 원본 그대로)
  - 내 형식 본문(`출력형식.js` `customText`·`customSections`)
- 핵심 요약형·업무 정리형 md decisions처럼 이미 `-`를 붙이는 곳은 기호를 한 곳에서만 붙임
- 여러 줄 옛 문단은 한 항목으로 보임(짝보고 3)
  - 화면은 항목 하나 안에서 줄을 바꿈
  - md·txt·복사는 이어지는 줄을 항목 본문과 같은 깊이로 들여 써서 하위 항목처럼 보이지 않게 함

## 알려진 영향

- 다시 분석·의견 반영 때 사람이 고친 할 일(체크·담당)은 할 일 글이 같을 때만 새 결과로 이어짐(`할일정리.js`·`Todos.java`)
  - 업데이트 전에 만든 회의를 처음 다시 분석하면 할 일 글이 문장형에서 짧은 꼴로 바뀌어 이어지지 않을 수 있음(짝 합성 대조로 확인)
  - 앞선 결과 버전의 체크·담당은 그 버전에 그대로 남음
- 고른 폴더 사본(`사본저장.cjs`·`Copies.java`)
  - 사본 기록에 지문이 있는 옛 회의를 다시 저장하면 글 모양이 바뀌어 새 사본 파일(예: `(2)`)이 생김
  - 지문이 없는 옛 사본 기록은 바뀐 것을 알아채지 못하고 건너뜀(옛 사본 그대로)
  - 이번 작업에서는 사본 규칙을 바꾸지 않음
- 옛 버전 앱이 새 결과를 여는 경우(앱을 낮춰 설치하거나 옛 실행 파일이 같은 자료 폴더를 여는 경우)
  - Windows는 저장 결과 검사에 막혀 열지 못함
  - 휴대폰은 검사 없이 열어 핵심 요약·주요 내용 등이 깨져 보일 수 있음
- 사람이 고친 할 일 글은 사람이 쓴 그대로 나감(AI 지시와 관계없음)

## 시험

- 바뀐 동작마다 먼저 실패하는 시험을 만든 뒤 고침
- 새로 필요한 시험
  - 옛 결과 바꾸기 — 문자열, overview 머리말 줄·다른 구분자 줄·여러 구분자·빈 내용, 겹친 글머리표, 빈 줄, 긴 문단, 13줄 넘는 overview, 반복 변환 같은 결과 — JS·Java 공통 예시
  - 두 가지 검사 — 옛 구조 응답은 AI 응답 검사에서 오류, 옛 구조 저장 결과는 열림, 새 구조 저장 결과도 열림
  - 원본 경계 — 옛 파일 바이트 불변, 옛·새 JSON 내보내기 모양, 저장 재시도 지문 불변, 고른 옛 버전 원본 보존
  - 빈 값 정리 — text만 빈 경우, details만 빈 경우, 머리말만 남은 경우, 빈 details 배열 — JS·Java 공통 예시
  - 결과 줄이기 — details만 줄어든 결과 받음, 내용이 다 빈 결과 거절, 거절 때 원래 결과 유지, 결정·미확정 details 그대로
  - 화면 — 목록·안쪽 목록, 옛 결과, 빈 칸, 긴 항목(Windows·휴대폰)
  - md·txt·복사 — 새 구조와 옛 구조, 기호 두 번 붙지 않음, 모든 저장 경로
  - 지시 — 개조식 규칙이 네 형식·줄이기·내 형식에 있고 문장형 요구("2~4문장의 문단", "완전한 문장" 등)가 없음
  - 길이 계산 — details까지 셈, JS·Java 같음, 응답 JSON 64,000자 한도 여유
- 함께 고칠 기존 시험(짝 보고 기준)
  - `출력형식.test.cjs`, `AI요청계약.test.cjs`, `요약입력.test.cjs`, `요약줄이기.test.cjs`, `회의문서.test.cjs`와 공통 예시 `desktop/tests/fixtures/회의문서-예시.json`, `회의흐름.test.cjs`, `할일저장.test.cjs`, `내할일화면.test.cjs`, `할일정리.test.cjs`, `사본저장.test.cjs`
  - 휴대폰 `내형식일치.test.cjs`, `요약규칙일치.test.cjs`, `출력형식.test.cjs`, `AndroidChecks.java`, 화면 검사
  - 사실 보존 시험은 의미를 지키며 문구만 맞춤, 지우지 않음
- 휴대폰 Java의 공통 예시 시험은 가상기기에서만 돎(PC의 JVM 시험은 org.json을 실행하지 못함)

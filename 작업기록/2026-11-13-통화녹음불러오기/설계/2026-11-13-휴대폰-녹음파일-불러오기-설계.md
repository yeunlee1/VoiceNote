# 휴대폰 녹음 파일 불러오기 설계 (tm 35·17)

통화 녹음 앱이 만든 m4a 파일을 VoiceNote 휴대폰 앱에서 골라, 앱에서 직접 녹음한 회의처럼 전사하고 정리까지 받게 한다. Windows 앱의 같은 문제(m4a 불러오기가 저장 단계에서 거절되던 것)는 tm 35.4에서 고쳐 짝 확인까지 마쳤고, 이 문서는 휴대폰 쪽만 다룬다.

## 사용자 요청과 결정

- "야 통화파일이 m4a파일인데 이거는 우리 분석이 안되네?" (2026-11-12)
- "휴대폰 불러오기도 같이해" (2026-11-13)
- 넘기는 방법: "앱 안에서 고르기 (Recommended)". 다른 앱에서 공유로 보내기는 고르지 않았다.
- 긴 통화: "자동으로 나눠 분석". 22MB를 넘는 파일을 앱이 잘라 차례로 전사한다.
- 나누는 방법: "1". 다시 압축하지 않고 잘라 담고, 앱 녹음과 같은 기준(20분이나 22MB 중 먼저 닿는 쪽)으로 나눈다.

## 지금 휴대폰 앱이 하는 일

- '회의 시작'을 누르면 화면 칸(회의명·날짜·참석자·출력 형식·상세 내용)으로 회의 기록을 만들고(`Store.create`), 녹음 서비스(`MeetingService`)가 `원음-001.m4a`부터 녹음한다. 녹음은 AAC·MPEG-4, 모노 24kHz 64kbps이고 20분이나 22MB에 닿으면 다음 파일로 넘어간다(`MeetingService.java:49-51`).
- '회의 종료'를 누르면 같은 서비스가 분석한다. `Ai.analyze`가 `record.audio`의 파일을 하나씩 `meeting.m4a`, `audio/mp4`로 전사하고(`Ai.java:59-71`, `144-150`), 전사를 이어 붙여 정리한다. 파일마다 전사를 `전사-NNN.txt`로 남겨 다시 분석할 때 재사용한다.
- 지난 회의 목록에서 '다시 분석'을 누르면 같은 분석이 저장된 원음으로 다시 돈다(`MainActivity` `analyze`).
- 다른 앱의 파일을 받아 오는 길은 없다. 파일 선택 창(SAF)은 설정 파일 내보내기·불러오기와 텍스트 저장에만 쓴다(`MainActivity.java:98-99`, `203-212`).
- 화면에는 '권한 요청이나 파일 선택을 먼저 마쳐 주세요.'라는 시작 막힘(`filePending`)이 이미 있다(`flow.js:27`).

## 목표

1. 새 회의 화면에 '녹음 파일 불러오기' 단추를 둔다. 누르면 휴대폰 파일 선택 창이 열리고 m4a 파일 하나를 고른다.
2. 고른 파일로 새 회의를 만들고 바로 분석한다. 회의명·날짜·참석자·출력 형식·상세 내용은 '회의 시작'과 똑같이 화면 칸의 값을 쓴다.
3. 파일이 20분과 22MB 안이면 바이트를 그대로 `원음-001.m4a`로 담는다. 넘으면 소리를 다시 압축하지 않고 20분이나 22MB 중 먼저 닿는 곳마다 잘라 `원음-001.m4a`, `원음-002.m4a`…로 담는다.
4. 그 뒤는 지금의 분석·지난 회의·다시 분석·사본 저장이 그대로 쓴다. 불러온 회의와 녹음한 회의를 다르게 다루지 않는다.

## 하지 않는 것

- 다른 앱에서 공유로 받기, 여러 파일을 한 번에 불러오기.
- MP4 계열(m4a·mp4)이 아닌 파일(wav·webm·mp3·amr·3gp 등). 휴대폰 분석 경로가 `audio/mp4`만 보내기 때문이다.
- 소리를 풀어 다시 압축하기, 조용한 곳을 찾아 자르기. 정해진 시간마다 자르므로 지금 앱 녹음처럼 나눈 지점에서 문장 하나가 끊길 수 있다.
- 원본 파일 이름이나 통화 상대 정보를 회의 기록에 저장하기.

## 실패로 볼 것

- 사용자가 고른 원본 파일을 바꾸거나 지운다.
- 지원하지 않는 파일을 받아 놓고 분석 단계에서야 실패한다.
- 분석이 실패했을 때 불러온 원음까지 잃는다. 지금 녹음처럼 원음은 남고 '다시 분석'할 수 있어야 한다.
- 복사·자르기가 중간에 실패해 원음이 빠진 회의가 목록에 남는다.

## 제약

- OpenAI 전사는 파일 하나에 25MB까지 받는다. 문서는 더 큰 녹음을 25MB 이하로 나누되 문장 중간을 피하라고 권한다(developers.openai.com/api/docs/guides/speech-to-text#longer-inputs). `gpt-transcribe` 모델 문서에는 길이 제한이 적혀 있지 않다.
- 휴대폰 앱은 전사 요청 하나를 5분까지 기다린다(`Ai.java:43` `setReadTimeout(300000)`). 22MB 안이라도 아주 긴 파일은 이 시간을 넘길 수 있어 20분 기준도 함께 쓴다.
- 파일은 저장소 접근 프레임워크(SAF)의 문서 선택 창으로만 읽는다. 새 저장소 권한을 요청하지 않는다.
- 키·체험 조건, 진행 중인 회의, 업데이트 설치 중 막힘은 '회의 시작'과 같다(`Flow.startBlockers`, `store.requireAccess`, `Updates.installing`).
- 공개 저장소다. 시험 자료는 합성 음성과 합성 이름(김민수·박서연·이도현·최유진)만 쓴다.
- 파일 선택 창과 자르기(MediaExtractor·MediaMuxer)는 Android에서만 돈다. 실제 동작 확인은 가상기기가 있어야 하고, 가상기기는 사용자 허락을 받고 띄운다.

## 방법

| 안 | 내용 | 얻는 것 | 잃는 것 |
|---|---|---|---|
| 1. 그대로 잘라 담기 (고름) | AAC m4a를 MediaExtractor로 읽어 소리를 풀지 않고 MediaMuxer로 새 m4a에 나눠 담는다 | 빠르다(1시간 통화도 몇 초). 음질 그대로. 새 라이브러리 없음 | AAC가 아닌 형식은 자를 수 없어 짧은 것만 받는다 |
| 2. 다시 압축하기 | 소리를 풀어 앱 녹음과 같은 64kbps AAC로 다시 만든다 | 거의 모든 형식 | 1시간 통화에 몇 분, 배터리, 만들 것이 많다 |
| 3. 크기만 보고 자르기 | 22MB가 넘을 때만 1번처럼 자른다 | 전사 요청 수가 가장 적다 | 22MB 안의 아주 긴 통화가 5분 대기에 걸릴 수 있다 |

사용자가 1번을 골랐다(2026-11-13). 기준은 앱 녹음과 같은 20분·22MB다.

## 정한 동작

### 화면

- 새 회의 화면의 준비 칸과 '시작 전 필요/준비 완료' 상자 아래에 보조 단추 '녹음 파일 불러오기'와 한 줄 설명을 둔다. 설명은 '통화 녹음 같은 m4a 파일을 골라 바로 분석합니다. 20분이 넘으면 나눠서 전사합니다.' 정도다. 주 단추는 계속 '회의 시작'이다.
- 단추는 '회의 시작'과 같은 조건(`Flow.canStart`)에서만 누를 수 있다. 막힌 이유는 지금 상자가 보여 준다.
- 누르면 파일 선택 창이 열리는 동안 `filePending`으로 다른 시작을 막는다. 고르기를 취소하면 아무것도 바꾸지 않고 원래 화면으로 돌아온다.
- 파일을 고른 뒤에는 녹음을 마친 회의와 같은 진행 화면(분석 단계, 진행 문구)으로 넘어간다. 준비하는 동안 문구는 '녹음 파일을 준비하는 중'이고, 나눴으면 '녹음 파일을 N개로 나눴습니다' 뒤에 지금의 '음성을 글로 변환 중 · 1 / N'이 이어진다.
- 성공해서 회의를 만들면 '회의 시작' 뒤처럼 회의명·참석자·상세 내용 칸을 비운다.

### 고른 파일 확인

- 파일 선택 창은 `ACTION_OPEN_DOCUMENT`, `CATEGORY_OPENABLE`, 형식 `audio/*`에 `audio/mp4`, `audio/x-m4a`, `audio/m4a`, `video/mp4`를 더해 연다. 형식 이름은 믿지 않고 내용으로 판정한다.
- 앞 12바이트의 offset 4가 `ftyp`가 아니면 거절한다. 안내: '‘<파일 이름>’ 파일은 불러올 수 없습니다. m4a 녹음 파일만 불러올 수 있습니다.' Windows 판정과 같다.
- 길이는 MediaExtractor의 오디오 트랙 길이로 읽는다. 오디오 트랙이 없으면 위와 같은 안내로 거절한다.
- 20분이나 22MB를 넘는데 오디오 트랙이 AAC(`audio/mp4a-latm`)가 아니면 거절한다. 안내: '‘<파일 이름>’ 파일은 20분(22MB)이 넘는데 나눌 수 없는 형식입니다. 20분 이하 파일만 불러올 수 있습니다.'
- 4시간이 넘는 파일은 거절한다(춘식 판단). 녹음 서비스가 잡는 화면 꺼짐 방지가 4시간이고, 실수로 고른 큰 파일의 전사 비용을 막는다.
- 휴대폰 남은 공간이 파일 크기와 여유 50MB를 합친 것보다 적으면 거절한다. 안내: '휴대폰 저장 공간이 부족해 파일을 불러오지 못했습니다.'
- 원본은 읽기만 한다. 쓰기·지우기·영구 접근 권한(`takePersistableUriPermission`)을 쓰지 않는다.

### 담기와 자르기

- 회의 기록을 만들기 전에 앱 안 임시 폴더(앱 파일 영역의 `불러오기-임시\<임시 id>\`)에 담는다. 다 담은 뒤에만 `Store.create`로 회의를 만들고 조각을 회의 폴더로 옮겨 `record.audio`에 차례로 적는다. 담는 중에 실패하거나 앱이 끝나면 임시 폴더만 지우고 회의는 만들지 않는다. 앱을 다시 열 때 남은 임시 폴더를 지운다.
- 20분과 22MB 안이면 원본 바이트를 그대로 `원음-001.m4a`로 복사한다.
- 넘으면 오디오 트랙의 샘플을 차례로 새 MPEG-4 파일에 옮긴다. 조각의 길이가 20분에 닿거나 크기가 약 20MB(22MB 상한 아래 여유)에 닿으면 다음 샘플부터 새 조각을 시작한다. 조각마다 시간은 0부터 다시 센다. AAC 프레임은 각각 따로 풀 수 있으므로 어느 프레임 경계에서 잘라도 된다.
- 마지막 조각이 아주 짧아도(예: 몇 초) 그대로 둔다(춘식 판단). 전사가 빈 글이면 지금처럼 다른 조각의 전사와 이어 붙인다.

### 서비스와 분석

- 담기·자르기도 녹음 서비스(`MeetingService`)가 새 동작(`import`)으로 맡는다(춘식 판단). 화면이 꺼지거나 다른 앱으로 넘어가도 알림을 띄운 채 이어 가고, 서비스가 일하는 동안(`active`)에는 지금처럼 다른 회의 시작과 업데이트 설치가 막힌다.
- 화면(`MainActivity`)은 파일을 고른 결과(문서 주소)와 화면 칸 값을 서비스에 넘긴다. 문서 선택 창이 준 읽기 권한은 같은 앱 안에서 유효하므로 서비스가 같은 주소를 연다.
- 다 담으면 같은 서비스 실행 안에서 지금의 `analyze()`로 넘어간다. 분석 실패, 다시 분석, 체험 횟수, 사본 저장은 지금 녹음과 똑같다.
- 담는 동안에는 회의 기록이 아직 없으므로, '녹음 파일을 준비하는 중' 같은 진행 문구는 서비스 상태(`MeetingService.snapshot`)로만 화면에 보낸다. 회의를 만든 뒤부터는 지금처럼 회의 기록의 `state`·`message`가 진행을 싣는다(실을 방식은 만드는 사람 판단).

## 시험과 확인

- JVM 단독 시험: 헤더 판정(ftyp, 12바이트 미만, 빈 파일), 나눌지 판정(20분·22MB·4시간 경계), 조각 경계 계산(예: 50분·30MB → 20·20·10분, 22MB 안 45분 → 20·20·5분), 안내 문구 선택.
- 가상기기 시험(`AndroidChecks`): 기기에서 합성 AAC m4a를 만든다(무음이나 사인파를 MediaCodec으로 압축). 시험용으로 기준을 몇 초로 낮춘 같은 자르기 코드로 나눠, 조각 수·조각마다 0부터 시작하는 시간·샘플 합계·MediaExtractor로 다시 읽히는지를 본다. 임시 폴더 정리와 실패 때 회의를 만들지 않는 것도 본다.
- 화면 시험: 모의 네이티브(`tests/설정평가-모의브리지.cjs`)에 `importAudio`를 더하고, 기존 헤드리스 Chrome 화면 검사로 단추의 켜짐·꺼짐, 취소, 거절 안내, 성공 뒤 진행 화면과 칸 비우기를 본다. 이고라이트로 휴대폰 폭(360·412) 캡처를 연다.
- 실제 확인: 가상기기에서 파일 선택 창으로 합성 m4a를 골라 담기·자르기·분석 시작까지 본다. 실제 OpenAI 전사는 사용자가 허락할 때만 하고, 실제 통화 녹음은 쓰지 않는다.

## 만드는 사람에게 남긴 것

- 단추와 설명의 정확한 문구와 자리, 진행 문구의 세부.
- 조각 크기 여유(약 20MB)와 임시 폴더 이름.
- 문서 선택 창에 넣을 형식 이름 목록의 세부.
- 서비스 상태로 진행 문구를 싣는 방식.

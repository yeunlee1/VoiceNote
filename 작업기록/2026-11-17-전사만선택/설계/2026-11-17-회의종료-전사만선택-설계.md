- 작업 브랜치 — `work/2026-11-17-전사만선택`

  - 같은 화면 파일(`app.js` 등)을 고친 tm 36 위에서 해야 충돌이 없음
- 함께 나가는 버전 — 1.7.0(tm 38 배포)

## 사용자 요청과 결정

- 「그리고 회의종료했을때 이거 회의록을 전사문까지만 요청할지. 아니면 회의록요약까지 요청할지 선택해서 진행하게해주면 좋을거같음.」
- 1.7.0에 넣기 — 「37까지 만들고 배포」
- 고르는 방법 — 「종료 때마다 작은 창에서 고름 (Recommended)」
- 전사만 한 회의를 나중에 회의록으로 — 「정리본 자리에 '회의록 만들기' 단추 (Recommended)」
- 녹음 파일 불러오기 — 「불러오기에도 넣기 (Recommended)」

## 목표

- 회의 종료와 녹음 파일 불러오기 때 '회의록까지 만들기'와 '전사까지만'을 고름
- 전사만 저장한 회의는 정리본 탭의 '회의록 만들기'로 이어서 만듦
  - 저장된 전사를 다시 써서 전사 비용이 다시 들지 않음
- Windows와 휴대폰이 같은 말·같은 순서로 동작함

## 하지 않는 것

- 고른 쪽 기억하기(아래 「정할 것」 1)
- 휴대폰 알림의 '회의 종료 · 분석' 단추에는 창을 띄우지 않음
  - 알림에서는 화면을 띄울 수 없어 지금처럼 회의록까지 만듦
- 전사만 저장할 때 사용자가 고른 폴더로 사본 보내기
- AI 지시·회의록 형식·개조식 규칙 변경

## 고르는 창

- 제목 — 「회의록을 어디까지 만들까요?」
- 단추 두 개와 닫기
  - [회의록까지 만들기] — 기본 단추, 처음 초점이 여기 있음
    - 설명 「전사한 뒤 회의록으로 정리합니다.」
  - [전사까지만] — 보조 단추
    - 설명 「전사문만 저장합니다. 회의록은 나중에 정리본 탭에서 만들 수 있습니다.」
  - 닫기(Esc·뒤로) — 이번에는 아무것도 요청하지 않음
    - 음성은 이미 저장돼 있음, 나중에 다시 분석하면 같은 창이 다시 뜸
- 창이 뜨는 때 — 아직 전사하지 않은 음성으로 분석을 시작할 때
  - 회의 종료 — 녹음을 바로 멈추고 음성을 저장한 뒤 뜸
  - 녹음 파일 불러오기
    - Windows — 파일을 고른 뒤 '저장·분석 다시 시도'를 누르면 저장한 뒤 뜸
    - 휴대폰 — 파일을 고르기 전에 뜸(고르자마자 저장·분석이 이어지는 지금 흐름을 지킴)
  - 음성만 저장된 회의를 다시 분석할 때
- 창이 뜨지 않는 때 — 전사가 이미 있음
  - 바로 회의록을 만듦(지금 '다시 분석'과 같음)

## 전사만 저장한 회의

- 지난 회의 목록 꼬리표 — 「전사만」
  - 지금은 Windows가 음성만 있는 회의와 같이 「분석 대기」로 보여 구분이 안 됨
- 열면 정리본 탭이 먼저 열림
  - Windows는 지금 전사문 탭이 먼저 열림, 이 규칙을 바꿈
  - 안내 「전사만 저장한 회의입니다. 전사문은 옆 ‘전사문’ 탭에 있습니다.」
  - [회의록 만들기] 단추 — 저장된 전사로 요약만 요청함
- 음성만 있는 회의의 정리본 탭 안내는 지금처럼 둠
  - Windows 안내가 가리키는 상자 이름(‘전사 원문 확인 · 다시 분석’)이 실제 이름(‘전사 고치기 · 다시 분석’)과 달라 함께 바로잡음

## Windows 동작

- `finishMeeting` — 음성 저장·키 확인 뒤, 전사하지 않은 음성이 남았으면 창을 띄움
  - 회의록까지 — 지금 `summarize()` 그대로
  - 전사까지만 — 새 `transcribeOnly()`
- `transcribeOnly()` — `paidTask` 안에서 차례로 함
  - 원음 전사(`requestTranscription`)
  - 전사를 회의 기록에 저장(`POST /api/recordings/{보관함}/{녹음}/transcript`, 지금 요약 전에 쓰는 경로)
  - 체험 확정(`settleTrial("finish")`), 지난 회의 목록 새로 읽기, 안내
- 서버 지난 회의 목록에 `transcribed` 칸 — 회의록 없이 저장된 전사가 있을 때만 참
- 결과 창 탭 규칙(`availableTab`) — 정리본 없이 전사만 있으면 정리본 탭
- 정리본 빈 화면(`renderMinutes`) — 전사가 있으면 안내와 [회의록 만들기](`summarize(true)`)

## 휴대폰 동작

- 회의 종료
  - 화면 → `call('finish', { hold: true })`
  - 서비스는 녹음을 멈추고 저장만 함(상태 `saved`, 「음성 저장 완료」)
  - 화면이 녹음이 멈춘 것을 확인한 뒤 창을 띄움
  - 고르면 `call('analyze', { 보관함, 회의, mode })` — 지금 '다시 분석'과 같은 길
- 녹음 파일 불러오기 — 창에서 고른 값을 `importAudio` 요청에 실어 서비스가 저장 뒤 그 방식으로 분석
- 서비스의 분석 방식
  - `minutes` — 지금 `Ai.run` 그대로
  - `transcript` — 새 `Ai.transcribeOnly`
    - 원음마다 `전사-NNN.txt`가 있으면 다시 쓰고 없으면 전사(지금 규칙), `전사.txt` 갱신
    - 요약 요청 없음, 체험 확정은 `Ai.run`과 같은 방식
    - 끝나면 상태 `transcribed`, 「전사 저장 완료」
- 지난 회의 꼬리표 `transcribed` → 「전사만」
- 끝 상태 처리 — 끝 문구 「전사 저장 완료」, 진행 단계는 끝, 정리본 탭을 엶
- 정리본 탭 — 전사가 있고 정리본이 없으면 안내와 [회의록 만들기]
  - 누르면 지금 '다시 분석'과 같은 호출(`call('analyze')`)
- '다시 분석'(접힌 묶음 안) — 전사가 없으면 같은 창을 띄움, 있으면 지금처럼 바로 회의록

## 체험(공용 기본 키 3회)

- 전사까지만도 1회로 셈 (내 판단)
  - 전사가 비용이 가장 큰 요청이고, 지금 Windows '원음 전사' 단추와 휴대폰 체험 규칙이 이미 이렇게 셈
- 나중에 '회의록 만들기'도 1회로 셈
  - 한 회의에 2회가 될 수 있음, 창 설명에는 넣지 않고 지금 체험 안내 문구를 그대로 씀

## 시험

- 먼저 실패하는 시험을 쓰고 고침
- Windows(가짜 응답, 실제 OpenAI 없음)
  - 회의 종료 → 창 → 전사까지만 — 전사 저장 요청 1번, 요약 요청 0번, 체험 확정 1번
  - 회의 종료 → 창 → 회의록까지 — 지금과 같은 요청 순서
  - 창 닫기 — AI 요청 없음, 음성 저장 유지, 다시 시도 단추 보임
  - 전사가 이미 있으면 창 없이 요약
  - 목록 꼬리표 「전사만」, 열면 정리본 탭과 [회의록 만들기], 누르면 요약 요청만
  - 원음 불러오기 → 저장·분석 다시 시도 → 창
- 서버 — 지난 회의 목록의 `transcribed` 칸
- 휴대폰 JVM·기기 검사(실제 API 0회)
  - `Ai.transcribe` — 전사 파일 재사용, 요약 요청 없음, 체험 1회
  - 서비스 `finish` hold — 녹음 멈춤·저장만, 분석 없음
  - `analyze` mode 전달
- 휴대폰 화면 검사(헤드리스 Chrome·모의 네이티브)
  - 종료 → 창 → `analyze`의 mode, 불러오기 창 → `importAudio`의 mode
  - 「전사만」 꼬리표, 정리본 탭 안내·단추, 끝 문구
- 바뀌는 기존 시험 — `내할일화면.test.cjs`(전사만 있으면 전사문 탭을 기대), `불러오기검증-화면.cjs`(누르자마자 불러오기 요청을 기대) 등은 새 동작에 맞게 고침
- 실제 화면 — 이고라이트로 Windows(1280·960·390), 휴대폰(360·412)의 창·정리본 단추, 가상기기에서 종료 → 전사까지만 → 회의록 만들기

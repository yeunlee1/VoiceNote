# 진행 표시 B안(보냄·받음 일지) 설계

## 사용자 요구와 결정
- 원문(2026-11-19) 「지금 전사문 api요청보내거나 회의요약 api요청 등등 시간이 오래걸리는 괜찮음. 하지만 이게 지금 보면 그냥 앱이 멈춰있는것처럼 보여서 그게 너무 짜증남. 이게 지금 요약이 되고있는건지 아니면 멈춘건지 그게 답답함 이부분이 확실히 좀 해결이 되었으면 좋겠음. 이거는 좀 시안 5개정도 만들어서 피드백을 어떻게 줄건지 보여주면 좋을거같음」
- 시안 5개(작업기록/2026-11-19-진행표시/시안/2026-11-19-진행표시-시안.html) 중 사용자 선택 「B로가자」
- 이 문서는 B안을 두 앱에 실제로 넣기 위한 설계임

## 목표
- 분석 중 앱과 OpenAI가 주고받은 일을 시각과 함께 한 줄씩 보임(보냄·받음·실패·취소·저장)
- 응답을 기다리는 동안 지난 시간과 최대 대기 시간(5분)이 1초마다 올라감
  - 화면이 멈춘 것이 아니라 응답을 기다리는 중이라는 것, 끝없이 기다리지 않는다는 것을 바로 알게 함
- Windows 화면, 휴대폰 화면, 휴대폰 알림에 같은 내용을 보임
- 휴대폰에서 음성을 올리다 네트워크가 멈추거나 응답이 끝없이 늦어지면 기다림을 끊고 실패로 알림

## 하지 않을 것
- 진행률(%)과 남은 시간 추정
  - 요청 하나가 끝나기 전에는 알 수 없는 값이라 지어내지 않음
- 응답을 조금씩 받는 방식(스트리밍) 전환
- 일지를 회의 기록에 영구 저장
  - 이번 분석 동안과 끝난 직후 화면에만 보임
- 휴대폰 분석 취소 단추 추가
  - 지금 휴대폰에는 분석 취소가 없음. 이번 범위에 넣지 않고 나중 후보로 남김
- 시안 A·C·D·E의 요소(단계 목록, 진행 막대, 오래 걸림 카드, 결과 미리보기)
- Windows 서버의 OpenAI 요청 방식, 제한 시간, 비용 계산 변경
- 알림 권한 요청 방식 변경

## 보이는 모습

### Windows 진행 칸(새 회의 흐름)
```
음성 저장 완료. 회의록 정리 응답을 기다리는 중입니다.      ← 지금 줄(#workflow-status), 단계가 바뀔 때만 바뀜
┌ AI 요청 기록 ─────────────────── 마지막 기록 20:42:30 ┐
│ 20:41:00  음성 저장함 · 3개                            │
│ 20:41:06  전사 요청 보냄 · 조각 1/3 · 4.1MB             │
│ 20:41:40  전사 받음 · 조각 1/3 · 2,310자                │
│ 20:42:30  회의록 정리 요청 보냄 · 구간 1/2              │
│ 지금      응답 기다리는 중 · 0:42 / 최대 5:00            │  ← 1초마다 올라감
└──────────────────────────────────────────────────────┘
OpenAI는 일을 다 마친 뒤 한꺼번에 답을 보내서, 기다리는 동안에는 시간만 올라갑니다.
[분석 취소]
```
- '마지막 기록'은 실제로 일이 생긴 줄의 시각임. 줄이 하나도 없으면 숨김
- 기다림 줄의 시각 칸은 '지금'으로 씀(일이 생긴 시각이 아님)

### 휴대폰 화면
- 지금 줄(#workflow) 아래 같은 일지를 최근 4줄만 보임
- 기다림 줄과 안내 한 줄은 Windows와 같은 문구

### 결과 화면에서 시작한 일
- 일지는 앱마다 하나뿐이고, 보이는 자리가 둘임
  - 새 회의 진행 칸(Windows #workflow-status 아래, 휴대폰 #workflow 아래)에는 늘 보임
  - 결과 화면이 열려 있고 그 화면의 회의가 지금 분석 중인 회의와 같으면 결과 화면에도 같은 일지를 보임
- Windows 결과 화면의 자리는 제목 아래 #result-status 바로 아래
  - 탭과 상관없이 보이므로 회의록 만들기, 원음 전사, 입력한 전사로 다시 분석, 의견 반영이 모두 여기에 보임
- 휴대폰 결과 화면의 자리는 #meeting-status 바로 아래
- 새 회의 진행 칸으로 옮겨 가게 하지 않음

### 휴대폰 알림
- 열린 요청이 있으면 내용은 그 이름(예: 「회의록 정리 · 구간 2/2 응답 기다리는 중」), 알림 옆 시간은 보낸 때부터 저절로 올라감(setWhen·setUsesChronometer, API 16부터라 지금 최소 지원 버전에서 쓸 수 있음)
- 요청이 닫히거나 바뀔 때 알림을 새로 고쳐 앞 요청의 시간이 남지 않게 함
- 열린 요청이 없으면 지금처럼 지금 줄 글을 보임
- 알림 권한이 꺼져 있으면 알림은 안 보이고 앱 안 일지만 보임

## 일지 줄의 뜻과 기록 규칙
- 두 층으로 적음
  - 요청 줄: 요청을 보내는 함수가 보냄과 응답(받음·실패)을 적음. 받음은 응답을 다 읽고 그 함수가 결과를 꺼낸 때임
  - 분석 줄: 분석 흐름이 내용 검사·저장·끝을 적음(형식 오류, 줄이기를 못 씀, 저장 실패, 전사 저장함, 회의록 저장함, 분석 취소함)
  - 그래서 요청은 받았는데 내용이 쓸 수 없거나 저장에 실패하면, 받음 줄은 그대로 두고 그 아래 분석 줄이 이어짐
- 보냄
  - Windows는 화면이 앱 안 서버에 요청을 넘긴 때(aiApi에 들어간 때). 서버는 바로 OpenAI로 보냄
  - 휴대폰은 OpenAI 연결을 열고 요청 본문을 쓰기 시작한 때
  - 보냄은 OpenAI가 받았다는 뜻이 아니므로 문구도 '요청 보냄'으로 씀
- 받아 둔 결과를 다시 쓴 경우는 보냄으로 적지 않고 「받아 둔 … 씀」 줄로 적음
- 시각은 일이 생긴 곳(Windows 화면 스크립트, 휴대폰 Ai)에서 기록함. 화면이 상태를 읽어 간 시각을 쓰지 않음
- 일지마다 번호(이번 분석의 일지 번호)를 붙이고 줄마다 순서 번호를 붙임
  - 화면은 일지 번호가 바뀌면 새로 그림. 앞 분석의 줄과 섞이지 않음
  - 한 번의 조회 사이에 보냄·받음·다음 보냄이 모두 일어나도 빠짐없이 보임
- 일지에 파일 이름, 전사·회의록 내용, API 키를 넣지 않음

## 기다림 줄 규칙
- 요청을 보낸 뒤 응답이 올 때까지 일지 맨 아래에 한 줄로 보이고, 1초마다 그 줄의 시간만 다시 씀
- 응답이 오면 받음 줄로 바뀌고, 실패하면 실패 줄로 바뀜
- Windows
  - 지난 시간은 화면이 보낸 때부터 잼. '최대 5:00'은 서버의 OpenAI 제한을 뜻함
  - 화면은 시간 초과를 스스로 정하지 않고 서버의 결과(받음 또는 시간 초과)를 기다림
  - 서버의 제한 시간은 서버가 본문을 다 받은 뒤부터라 화면의 5:00과 조금 어긋날 수 있음(같은 PC 안이라 보통 몇 초)
  - 5:00을 넘었는데 아직 결과가 없으면 「응답 기다리는 중 · 5:03 · 제한 시간이 지나면 서버가 실패로 알려 줌」으로 보임. 언제 멈출지 단정하지 않음
  - 그 뒤 늦게 받으면 보통 받음 줄로 바뀌고, 서버가 시간 초과를 알리면 그때 「응답 없음」 줄로 바뀜
- 휴대폰
  - 올리는 동안 「음성 올리는 중 · 2.1/4.1MB」를 보임. 양은 앱이 연결에 넘긴 양이라 실제 도착량보다 조금 앞설 수 있음

## 휴대폰 구현 방향
- 일지 전달
  - MeetingService가 작업마다 일지 객체(ActivityLog)를 만들어 Ai에 넘기고, Ai가 보냄·올린 양·받음·실패와 분석 줄을 그 일지에 적음(기존 Progress.update(String)은 그대로 둠)
  - MeetingService는 이번 작업의 일지(일지 번호, 최대 30줄)와 열린 요청을 메모리에 들고 snapshot에만 실음
  - 회의 파일(record)에는 저장하지 않고, 일지가 바뀔 때 store.save를 부르지 않음(지금 줄이 바뀔 때의 저장은 그대로)
  - 올린 양은 1초에 한 번까지만 snapshot에 반영함
- 화면(assets/app.js)은 조회로 받은 일지를 그리고, 기다림 줄은 1초 타이머로 시간만 바꿈
- 알림은 위 「휴대폰 알림」대로 고침
- 요청 감시(OpenAI 요청 두 곳 모두)
  - 시간 계산은 단조 시계(System.nanoTime)로 하고, 일지에 보이는 시각만 기기 시계로 씀
    - 분석 중에는 partial wake lock으로 CPU가 깨어 있어 잠자는 시간이 끼지 않음. java.*만 써서 PC JVM 시험으로도 확인할 수 있음
  - 올리기: 감시는 연결을 열기 시작할 때(getOutputStream 전) 시작하고, 연결이 열림·쓰기 한 번 끝남·본문 닫기 끝남마다 '진행'으로 시각을 새로 씀. 마지막 진행 뒤 60초 넘게 다음 진행이 없으면 끊음 → 「음성 올리기 멈춤」(회의록 요청은 「요청 보내기 멈춤」)
    - 그래서 첫 쓰기에서 멈추거나 닫기(flush·close)에서 멈춰도 60초 뒤 끊김
  - 회의록 요청은 본문 크기를 알고 있으므로 setFixedLengthStreamingMode로 바로 보내게 바꿔, 두 요청 모두 '본문을 다 쓰고 닫은 때'를 다 올린 때로 씀
  - 응답: 다 올린 때부터 응답 머리와 본문을 다 읽을 때까지 전체 5분을 넘으면 끊음 → 「응답 없음」
  - 끊기는 감시 스레드가 연결을 닫는 방식(disconnect)으로 함
    - API 26·35 표준 구현에서 disconnect가 소켓을 닫아 막힌 쓰기·읽기를 푸는 경로를 짝이 소스로 확인함
    - 실제로 풀리는지는 로컬 가짜 서버 시험으로 먼저 확인하고, 안 풀리면 전송 방식과 문구를 다시 정함
- 의견 반영과 전사만 하기도 같은 일지를 씀
